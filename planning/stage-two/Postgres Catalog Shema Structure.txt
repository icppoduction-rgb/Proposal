ФИНАЛЬНАЯ СТРУКТУРА POSTGRESQL CATALOG SCHEMA ДЛЯ STAGE TWO
Проект: Proposal — Behaviour-driven hybrid learning for data exfiltration detection
Назначение: PostgreSQL catalog для управления Stage Two: Data Normalization

================================================================================
1. ОБЩАЯ ЦЕЛЬ POSTGRESQL CATALOG
================================================================================

PostgreSQL в данном проекте не используется как хранилище всех больших данных.
Его задача — быть управляющим каталогом pipeline.

PostgreSQL должен хранить:
- какие датасеты используются;
- какие raw-файлы найдены;
- к какой роли относится каждый файл: TRAIN, VALIDATION, TEST, EXPERIMENTS;
- к какой ветке относится файл: dns, host, network, hybrid;
- какой parser назначен или использован;
- какая версия parser-а и schema применялась;
- куда сохранены normalized Parquet artifacts;
- куда сохранены feature Parquet artifacts;
- куда сохранены model-ready artifacts;
- сколько строк/событий прочитано, обработано и упало;
- какие quality checks были выполнены;
- какие ошибки возникли;
- как связать model-ready данные обратно с исходным raw-файлом.

Большие данные PostgreSQL хранить не должен.

Большие данные должны храниться в:
- Parquet — normalized events, features, model-ready tabular datasets;
- NPZ / similar — sequence windows для LSTM;
- raw layer — исходные файлы датасетов без изменений.

DuckDB используется отдельно как аналитический SQL-движок поверх Parquet.

Итоговая логика:

RAW DATASETS
    ↓
CATALOG INGESTION
    ↓
PARSER ROUTING
    ↓
NORMALIZED EVENTS
    ↓
PARQUET STORAGE
    ↓
FEATURE EXTRACTION
    ↓
MODEL-READY DATASETS
    ↓
TRAIN / VALIDATION / TEST

PostgreSQL catalog нужен для контроля всех переходов между этими слоями.

================================================================================
2. СВЯЗЬ С PATH_DATA_STORAGE
================================================================================

Рекомендуемая структура хранения:

${PATH_DATA_STORAGE}/
├── postgres/
├── pgadmin/
├── parquet/
│   ├── normalized/
│   ├── features/
│   └── model_ready/
├── duckdb/
├── reports/
├── logs/
├── backups/
└── temp_data/

Что где хранится:

1. ${PATH_DATA_STORAGE}/postgres/
   - физические данные PostgreSQL container volume;
   - управляется Docker/PostgreSQL;
   - вручную не редактировать.

2. ${PATH_DATA_STORAGE}/pgadmin/
   - данные pgAdmin;
   - настройки подключения, сессии, metadata pgAdmin.

3. ${PATH_DATA_STORAGE}/parquet/normalized/
   - normalized events после parsing/normalization;
   - DNS events, host events, network flows, syscall/API events, logs, metrics.

4. ${PATH_DATA_STORAGE}/parquet/features/
   - feature tables после feature extraction;
   - dns_features, host_syscall_features, host_eventlog_features, network_flow_features, hybrid_features.

5. ${PATH_DATA_STORAGE}/parquet/model_ready/
   - финальные таблицы для ML/DL;
   - X_train.parquet, y_train.parquet, X_validation.parquet, X_test.parquet и т.д.

6. ${PATH_DATA_STORAGE}/duckdb/
   - DuckDB database files, если будут использоваться постоянные .duckdb файлы.

7. ${PATH_DATA_STORAGE}/reports/
   - parser reports;
   - normalization reports;
   - data quality reports;
   - schema mismatch reports;
   - leakage check reports.

8. ${PATH_DATA_STORAGE}/logs/
   - runtime logs pipeline;
   - ошибки ingestion, parser routing, normalization.

9. ${PATH_DATA_STORAGE}/backups/
   - резервные копии catalog metadata или важных configuration artifacts.

10. ${PATH_DATA_STORAGE}/temp_data/
   - промежуточные JSON/temporary artifacts;
   - уже используется в Stage One для inventory/sort summaries.

Важно:
В PostgreSQL лучше хранить относительные пути от PATH_DATA_STORAGE, например:

parquet/normalized/dns/train/part-0001.parquet

А не абсолютные пути вида:

C:\Users\Public\PythonProjects\storage\parquet\normalized\dns\train\part-0001.parquet

Причина:
- проект легче переносить на другую машину;
- PATH_DATA_STORAGE может измениться;
- catalog остается стабильным.

3. ОБЯЗАТЕЛЬНЫЕ ТАБЛИЦЫ CATALOG SCHEMA
================================================================================

Финальная структура должна включать следующие таблицы:

1. datasets
2. ingestion_runs
3. dataset_files
4. parser_registry
5. parser_runs
6. schema_versions
7. normalized_artifacts
8. feature_artifacts
9. model_ready_artifacts
10. data_quality_reports

Эти таблицы покрывают полный Stage Two lifecycle:

datasets
    ↓
dataset_files
    ↓
parser_runs
    ↓
normalized_artifacts
    ↓
feature_artifacts
    ↓
model_ready_artifacts
    ↓
data_quality_reports

ingestion_runs фиксирует запуски сканирования raw datasets.
parser_registry фиксирует доступные parser-ы.
schema_versions фиксирует версии normalized/feature/model-ready схем.

================================================================================
4. ТАБЛИЦА datasets
================================================================================

Назначение:
Хранит список датасетов, которые используются в проекте.

Примеры датасетов:
- CIC-Bell-DNS-EXF-2021
- CIC-Bell-DNS-2021
- Mendeley DNS Exfiltration Dataset
- ADFA IDS
- LID-DS 2021
- Maintainable Log Dataset
- LID-DS 2019
- LANL Dataset
- Windows Event Log / OTRF Security Datasets
- Unified Host + Network Dataset / LANL
- ISOT Cloud IDS Dataset
- Dynamic Malware Analysis Dataset

Зачем нужна:
- отделяет dataset-level metadata от file-level metadata;
- позволяет хранить роль датасета;
- позволяет не дублировать dataset_name в каждой таблице;
- нужна для связи raw-файлов, normalized artifacts, feature artifacts и model-ready artifacts.

Рекомендуемые поля:

- id
  Уникальный идентификатор датасета.

- name
  Название датасета.

- branch
  Ветка данных:
  dns / host / network / hybrid

- role
  Роль датасета:
  TRAIN / VALIDATION / TEST / EXPERIMENTS

- source_group
  Группа источника, например:
  DNS benchmark, HIDS benchmark, enterprise logs, cloud telemetry, malware sandbox.

- description
  Краткое описание датасета.

- is_active
  Используется ли датасет в текущем scope проекта.

- created_at
  Дата создания записи.

Рекомендуемый SQL:

CREATE TABLE IF NOT EXISTS datasets (
    id SERIAL PRIMARY KEY,
    name TEXT NOT NULL,
    branch TEXT NOT NULL,
    role TEXT NOT NULL,
    source_group TEXT,
    description TEXT,
    is_active BOOLEAN DEFAULT TRUE,
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    CONSTRAINT chk_datasets_branch
        CHECK (branch IN ('dns', 'host', 'network', 'hybrid')),
    CONSTRAINT chk_datasets_role
        CHECK (role IN ('TRAIN', 'VALIDATION', 'TEST', 'EXPERIMENTS')),
    CONSTRAINT uq_datasets_name_branch_role
        UNIQUE (name, branch, role)
);

Почему UNIQUE важен:
Один и тот же датасет не должен случайно регистрироваться несколько раз в одной и той же ветке и роли.

================================================================================
5. ТАБЛИЦА ingestion_runs
================================================================================

Назначение:
Фиксирует каждый запуск catalog ingestion, то есть каждый запуск сканирования raw datasets.

Catalog ingestion — это этап, когда pipeline проходит по папкам raw datasets и регистрирует найденные файлы в PostgreSQL.

Эта таблица отвечает на вопросы:
- когда выполнялось сканирование;
- какой root path сканировался;
- какая ветка сканировалась;
- какая роль сканировалась;
- сколько файлов найдено;
- сколько файлов новых;
- сколько уже существовало;
- сколько изменилось;
- сколько файлов не удалось обработать;
- завершился ли запуск успешно.

Зачем нужна:
Без ingestion_runs будет сложно понять, каким запуском был найден файл и какой результат был у конкретного scan.

Рекомендуемые поля:

- id
  Уникальный идентификатор запуска.

- run_name
  Человекочитаемое имя запуска, например:
  initial_dns_scan_2026_06_09

- root_path
  Корневая папка, которую сканировали.

- branch
  dns / host / network / hybrid.
  Может быть NULL, если сканировались все ветки.

- role
  TRAIN / VALIDATION / TEST / EXPERIMENTS.
  Может быть NULL, если сканировались все роли.

- started_at
  Время начала запуска.

- finished_at
  Время завершения запуска.

- status
  RUNNING / SUCCESS / PARTIAL_SUCCESS / FAILED.

- files_seen
  Сколько файлов найдено всего.

- files_new
  Сколько новых файлов добавлено в catalog.

- files_existing
  Сколько файлов уже было в catalog.

- files_changed
  Сколько файлов изменилось по hash/size/modified_at.

- files_failed
  Сколько файлов не удалось зарегистрировать.

- error_message
  Общая ошибка запуска, если была.

Рекомендуемый SQL:

CREATE TABLE IF NOT EXISTS ingestion_runs (
    id SERIAL PRIMARY KEY,
    run_name TEXT,
    root_path TEXT NOT NULL,
    branch TEXT,
    role TEXT,
    started_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    finished_at TIMESTAMP,
    status TEXT DEFAULT 'RUNNING',
    files_seen BIGINT DEFAULT 0,
    files_new BIGINT DEFAULT 0,
    files_existing BIGINT DEFAULT 0,
    files_changed BIGINT DEFAULT 0,
    files_failed BIGINT DEFAULT 0,
    error_message TEXT,
    CONSTRAINT chk_ingestion_runs_branch
        CHECK (branch IS NULL OR branch IN ('dns', 'host', 'network', 'hybrid')),
    CONSTRAINT chk_ingestion_runs_role
        CHECK (role IS NULL OR role IN ('TRAIN', 'VALIDATION', 'TEST', 'EXPERIMENTS')),
    CONSTRAINT chk_ingestion_runs_status
        CHECK (status IN ('RUNNING', 'SUCCESS', 'PARTIAL_SUCCESS', 'FAILED'))
);

================================================================================
6. ТАБЛИЦА dataset_files
================================================================================

Назначение:
Самая важная таблица для raw layer.
Хранит все исходные файлы, найденные в датасетах.

Каждая запись = один raw-файл.

Примеры файлов:
- DNS CSV;
- DNS PCAP;
- domain-list TXT;
- host JSON;
- syscall trace TXT;
- BSON sandbox telemetry;
- Windows/Sysmon JSON Lines;
- NetFlow files;
- raw logs;
- PCAP/PCAPNG/CAP network captures.

Зачем нужна:
- это точка входа для parser routing;
- через нее обеспечивается traceability;
- она связывает raw file → parser run → normalized artifact → feature artifact → model-ready artifact;
- позволяет не потерять исходный контекст.

Рекомендуемые поля:

- id
  Уникальный идентификатор raw-файла.

- dataset_id
  Ссылка на datasets.id.

- ingestion_run_id
  Ссылка на ingestion_runs.id.
  Показывает, каким scan-запуском файл был найден.

- file_path
  Полный или проектный путь к raw-файлу.

- relative_path
  Относительный путь от root dataset folder или PATH_DATA_STORAGE.
  Нужен для переносимости.

- file_name
  Имя файла.

- source_format
  Нормализованное имя формата:
  csv, json, jsonl, log, txt, pcap, pcapng, cap, bson, netflow_day, wls_day, xml и т.д.

- file_extension
  Физическое расширение файла:
  .csv, .json, .txt, .pcap и т.д.
  Иногда source_format и file_extension могут отличаться.

- file_size_bytes
  Размер файла в байтах.

- file_hash
  Hash файла.
  Нужен для контроля неизменности raw-файла.

- checksum_algorithm
  Алгоритм hash, например sha256.

- role
  TRAIN / VALIDATION / TEST / EXPERIMENTS.

- branch
  dns / host / network / hybrid.

- status
  Текущий статус файла в pipeline.

- last_seen_at
  Когда файл последний раз был найден scan-ом.

- modified_at
  Время изменения файла на файловой системе.

- is_empty
  Флаг пустого файла.

- parser_name
  Назначенный parser.

- parser_version
  Версия назначенного parser-а.

- schema_version
  Версия schema, которую планируется применить.

- label_source
  Откуда будет извлекаться label:
  filename / directory / column / metadata / external_mapping / unknown.

- timestamp_source
  Откуда будет извлекаться timestamp:
  column / packet_timestamp / event_order / relative_time / missing / unknown.

- error_message
  Ошибка регистрации или routing, если была.

- created_at
  Когда запись создана.

Рекомендуемый SQL:

CREATE TABLE IF NOT EXISTS dataset_files (
    id SERIAL PRIMARY KEY,
    dataset_id INTEGER NOT NULL REFERENCES datasets(id),
    ingestion_run_id INTEGER REFERENCES ingestion_runs(id),
    file_path TEXT NOT NULL,
    relative_path TEXT,
    file_name TEXT NOT NULL,
    source_format TEXT NOT NULL,
    file_extension TEXT,
    file_size_bytes BIGINT,
    file_hash TEXT,
    checksum_algorithm TEXT DEFAULT 'sha256',
    role TEXT NOT NULL,
    branch TEXT NOT NULL,
    status TEXT DEFAULT 'NEW',
    last_seen_at TIMESTAMP,
    modified_at TIMESTAMP,
    is_empty BOOLEAN DEFAULT FALSE,
    parser_name TEXT,
    parser_version TEXT,
    schema_version TEXT,
    label_source TEXT,
    timestamp_source TEXT,
    error_message TEXT,
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    CONSTRAINT chk_dataset_files_branch
        CHECK (branch IN ('dns', 'host', 'network', 'hybrid')),
    CONSTRAINT chk_dataset_files_role
        CHECK (role IN ('TRAIN', 'VALIDATION', 'TEST', 'EXPERIMENTS')),
    CONSTRAINT chk_dataset_files_status
        CHECK (status IN (
            'NEW',
            'REGISTERED',
            'READY_FOR_PARSING',
            'PARSING',
            'PARSED',
            'PARTIALLY_PARSED',
            'FAILED',
            'SKIPPED',
            'NORMALIZED',
            'FEATURE_EXTRACTED',
            'MODEL_READY',
            'NO_PARSER_AVAILABLE',
            'EMPTY_FILE'
        ))
);

Рекомендуемые индексы:

CREATE UNIQUE INDEX IF NOT EXISTS uq_dataset_files_dataset_path
ON dataset_files(dataset_id, file_path);

CREATE INDEX IF NOT EXISTS idx_dataset_files_dataset_id
ON dataset_files(dataset_id);

CREATE INDEX IF NOT EXISTS idx_dataset_files_ingestion_run_id
ON dataset_files(ingestion_run_id);

CREATE INDEX IF NOT EXISTS idx_dataset_files_branch_role_format
ON dataset_files(branch, role, source_format);

CREATE INDEX IF NOT EXISTS idx_dataset_files_status
ON dataset_files(status);

CREATE INDEX IF NOT EXISTS idx_dataset_files_hash
ON dataset_files(file_hash);

Почему это важно:
- UNIQUE защищает от повторной регистрации одного и того же файла;
- branch/role/source_format нужен для parser routing;
- status нужен для поиска файлов, готовых к следующему этапу;
- hash нужен для проверки, что raw-файл не изменился.

================================================================================
7. ТАБЛИЦА parser_registry
================================================================================

Назначение:
Хранит список доступных parser-ов и правила их применимости.

Эта таблица нужна для parser routing.

Пример:
- dns + csv → DnsCsvParser
- dns + pcap → DnsPcapParser
- host + bson → HostBsonParser
- host + txt → HostTxtTraceParser
- host + wls_day → WindowsEventLogParser
- network + netflow_day → NetFlowParser

Зачем нужна:
- routing становится управляемым и документированным;
- можно отключать parser через is_active;
- можно фиксировать parser_version;
- можно связать parser с output_schema_version.

Рекомендуемые поля:

- id
  Уникальный идентификатор parser-а.

- parser_name
  Имя parser-а.

- parser_version
  Версия parser-а.

- branch
  Для какой ветки parser:
  dns / host / network / hybrid.

- source_format
  Для какого формата parser.

- supported_role
  Для какой роли подходит:
  TRAIN / VALIDATION / TEST / EXPERIMENTS.
  Может быть NULL, если parser подходит для всех ролей.

- output_schema_version
  Какая schema получается на выходе parser-а.

- is_active
  Активен ли parser.

- description
  Описание parser-а.

- created_at
  Время создания записи.

Рекомендуемый SQL:

CREATE TABLE IF NOT EXISTS parser_registry (
    id SERIAL PRIMARY KEY,
    parser_name TEXT NOT NULL,
    parser_version TEXT NOT NULL,
    branch TEXT NOT NULL,
    source_format TEXT NOT NULL,
    supported_role TEXT,
    output_schema_version TEXT,
    is_active BOOLEAN DEFAULT TRUE,
    description TEXT,
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    CONSTRAINT chk_parser_registry_branch
        CHECK (branch IN ('dns', 'host', 'network', 'hybrid')),
    CONSTRAINT chk_parser_registry_supported_role
        CHECK (supported_role IS NULL OR supported_role IN ('TRAIN', 'VALIDATION', 'TEST', 'EXPERIMENTS')),
    CONSTRAINT uq_parser_registry
        UNIQUE (parser_name, parser_version, branch, source_format, supported_role)
);

Рекомендуемый индекс:

CREATE INDEX IF NOT EXISTS idx_parser_registry_lookup
ON parser_registry(branch, source_format, supported_role, is_active);

================================================================================
8. ТАБЛИЦА parser_runs
================================================================================

Назначение:
Фиксирует каждый запуск parser-а по конкретному файлу.

Если dataset_files говорит: “файл существует”,
то parser_runs говорит: “мы пытались его разобрать таким parser-ом, в такой версии, с таким результатом”.

Зачем нужна:
- можно повторять parsing разными версиями parser-а;
- можно видеть историю ошибок;
- можно сравнивать rows_read / rows_parsed / rows_failed;
- можно связать parser run с output Parquet.

Рекомендуемые поля:

- id
  Уникальный идентификатор parser run.

- file_id
  Ссылка на dataset_files.id.

- parser_name
  Имя parser-а.

- parser_version
  Версия parser-а.

- schema_version
  Версия normalized schema.

- started_at
  Время начала parsing.

- finished_at
  Время завершения parsing.

- status
  RUNNING / SUCCESS / PARTIAL_SUCCESS / FAILED / SKIPPED.

- rows_read
  Сколько строк/событий прочитано.

- rows_parsed
  Сколько строк/событий успешно разобрано.

- rows_failed
  Сколько строк/событий не удалось разобрать.

- error_message
  Ошибка, если была.

- output_parquet_path
  Путь к normalized Parquet, если parser уже пишет output.

Рекомендуемый SQL:

CREATE TABLE IF NOT EXISTS parser_runs (
    id SERIAL PRIMARY KEY,
    file_id INTEGER NOT NULL REFERENCES dataset_files(id),
    parser_name TEXT NOT NULL,
    parser_version TEXT NOT NULL,
    schema_version TEXT,
    started_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    finished_at TIMESTAMP,
    status TEXT DEFAULT 'RUNNING',
    rows_read BIGINT DEFAULT 0,
    rows_parsed BIGINT DEFAULT 0,
    rows_failed BIGINT DEFAULT 0,
    error_message TEXT,
    output_parquet_path TEXT,
    CONSTRAINT chk_parser_runs_status
        CHECK (status IN ('RUNNING', 'SUCCESS', 'PARTIAL_SUCCESS', 'FAILED', 'SKIPPED'))
);

Рекомендуемые индексы:

CREATE INDEX IF NOT EXISTS idx_parser_runs_file_id
ON parser_runs(file_id);

CREATE INDEX IF NOT EXISTS idx_parser_runs_status
ON parser_runs(status);

CREATE INDEX IF NOT EXISTS idx_parser_runs_parser
ON parser_runs(parser_name, parser_version);

================================================================================
9. ТАБЛИЦА schema_versions
================================================================================

Назначение:
Хранит версии схем данных.

Нужна для:
- normalized event schema;
- DNS feature schema;
- host syscall feature schema;
- host eventlog feature schema;
- network flow feature schema;
- hybrid feature schema;
- model-ready schema.

Зачем нужна:
Если структура normalized_events изменится, нужно знать, какие Parquet artifacts были созданы по старой схеме, а какие по новой.

Рекомендуемые поля:

- id
  Уникальный идентификатор schema version.

- schema_name
  Название схемы:
  normalized_events, dns_features, host_syscall_features, network_flow_features и т.д.

- schema_version
  Версия, например v1.0.

- layer
  На каком слое используется:
  normalized / features / model_ready.

- branch
  dns / host / network / hybrid.
  Может быть NULL, если схема общая.

- description
  Описание схемы.

- is_active
  Активна ли версия.

- created_at
  Время создания записи.

Рекомендуемый SQL:

CREATE TABLE IF NOT EXISTS schema_versions (
    id SERIAL PRIMARY KEY,
    schema_name TEXT NOT NULL,
    schema_version TEXT NOT NULL,
    layer TEXT NOT NULL,
    branch TEXT,
    description TEXT,
    is_active BOOLEAN DEFAULT TRUE,
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    CONSTRAINT chk_schema_versions_layer
        CHECK (layer IN ('normalized', 'features', 'model_ready')),
    CONSTRAINT chk_schema_versions_branch
        CHECK (branch IS NULL OR branch IN ('dns', 'host', 'network', 'hybrid')),
    CONSTRAINT uq_schema_versions
        UNIQUE (schema_name, schema_version, layer, branch)
);

================================================================================
10. ТАБЛИЦА normalized_artifacts
================================================================================

Назначение:
Хранит ссылки на normalized Parquet artifacts.

После parsing/normalization raw-файл превращается в normalized events.
Эти events сохраняются в Parquet.
PostgreSQL хранит не сами events, а путь к Parquet и metadata.

Зачем нужна:
- связывает raw-файл с normalized Parquet;
- фиксирует row_count;
- фиксирует schema_version;
- фиксирует статус нормализации;
- нужна для дальнейшего feature extraction.

Рекомендуемые поля:

- id
  Уникальный идентификатор artifact.

- dataset_id
  Ссылка на datasets.id.

- file_id

15. КАК ЭТА СХЕМА ПРЕДОТВРАЩАЕТ DATA LEAKAGE
================================================================================

Data leakage — это ситуация, когда TEST данные случайно используются при обучении, настройке preprocessing или выборе threshold.

В проекте нужно строго соблюдать:

1. TRAIN
   Используется для:
   - fit scaler;
   - fit encoder;
   - fit feature selector;
   - training model.

2. VALIDATION
   Используется для:
   - threshold tuning;
   - false positive control;
   - model/config selection.

3. TEST
   Используется только для:
   - финальной оценки;
   - external generalization check.

Как catalog помогает:

- datasets.role фиксирует роль датасета.
- dataset_files.role фиксирует роль каждого raw-файла.
- normalized_artifacts.role фиксирует роль normalized Parquet.
- feature_artifacts.role фиксирует роль feature Parquet.
- model_ready_artifacts.role фиксирует роль финальных ML/DL данных.
- CHECK constraints не дают записать неправильные role.
- индексы позволяют быстро проверить, не смешаны ли роли.
- preprocessing objects должны регистрироваться с role = TRAIN или как preprocessing_object, но fit должен выполняться только на TRAIN.

Критичное правило:
Если role датасета изменилась после создания feature/model-ready artifacts, pipeline должен пересобраться заново.

================================================================================
16. КАК ЭТА СХЕМА ОБЕСПЕЧИВАЕТ TRACEABILITY
================================================================================

Traceability — возможность пройти назад от model-ready данных к исходному raw-файлу.

Пример цепочки:

model_ready_artifacts.artifact_path
    ↓
feature_artifacts.feature_path
    ↓
normalized_artifacts.normalized_path
    ↓
parser_runs.file_id
    ↓
dataset_files.file_path
    ↓
datasets.name

Это значит:
для любого X_train.parquet или train_sequences.npz можно понять:
- из каких feature artifacts он был собран;
- из каких normalized events эти features были получены;
- каким parser-ом были разобраны raw-файлы;
- из каких исходных файлов пришли события;
- к какому датасету относится файл;
- какая у него роль: TRAIN / VALIDATION / TEST;
- какой hash был у raw-файла;
- какая версия parser-а и schema использовалась.

Это критично для воспроизводимости дипломного проекта.

20. КРАТКИЙ ИТОГ
================================================================================

Финальная PostgreSQL catalog schema нужна для того, чтобы Stage Two был управляемым, воспроизводимым и безопасным.

Главные функции catalog schema:

1. Управление датасетами.
2. Регистрация raw-файлов.
3. Фиксация ingestion-запусков.
4. Поддержка parser routing.
5. Фиксация parser runs.
6. Контроль schema versions.
7. Связь raw → normalized → features → model-ready.
8. Хранение путей к Parquet artifacts.
9. Контроль качества данных.
10. Предотвращение data leakage.
11. Полная traceability до исходного raw-файла.

Главный принцип:

PostgreSQL = metadata catalog + pipeline control.
Parquet = large normalized/features/model-ready data.
DuckDB = SQL analytics over Parquet.
Raw files = unchanged source of truth.
