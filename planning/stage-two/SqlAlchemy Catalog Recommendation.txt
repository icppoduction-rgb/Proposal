ОБНОВЛЕННАЯ РЕКОМЕНДАЦИЯ ПО SQLALCHEMY ДЛЯ STAGE TWO
================================================================================

1. ФИНАЛЬНОЕ РЕШЕНИЕ
================================================================================

SQLAlchemy использовать нужно.

Роль SQLAlchemy:
- основной Python access layer к PostgreSQL catalog;
- catalog ingestion;
- parser registry lookup;
- parser_runs lifecycle;
- artifact registry;
- data quality report registry;
- traceability queries.

SQLAlchemy не использовать для:
- хранения normalized events;
- хранения feature matrix;
- чтения PCAP/BSON/raw logs;
- аналитики по Parquet;
- training/inference data storage.

Формула:

SQLAlchemy + Alembic + PostgreSQL catalog = да.
SQLAlchemy для больших данных = нет.
DuckDB + Parquet для больших SQL-выборок = да.

3. CONFIG LAYER
================================================================================

scripts/db/config.py должен:
- читать DATABASE_URL из environment/.env;
- валидировать, что DATABASE_URL задан;
- не содержать credentials в коде;
- поддерживать testing DATABASE_URL override;
- возвращать immutable config object.

Пример публичного интерфейса:

class DatabaseSettings:
    database_url: str
    echo_sql: bool = False
    pool_pre_ping: bool = True

4. SESSION LAYER
================================================================================

scripts/db/session.py должен:
- создать SQLAlchemy engine;
- создать sessionmaker;
- дать context manager для транзакций;
- гарантировать rollback при exception;
- не скрывать IntegrityError.

Публичный интерфейс:

- get_engine(settings: DatabaseSettings) -> Engine
- create_session_factory(engine: Engine) -> sessionmaker[Session]
- session_scope() -> Iterator[Session]

Правила транзакций:
- маленькие операции: одна транзакция на бизнес-операцию;
- bulk ingestion: batch transactions;
- не держать одну огромную транзакцию на сотни тысяч файлов;
- не делать commit после каждого файла;
- все partial failures отражать в ingestion_runs/parser_runs.

5. ORM VS CORE
================================================================================

Использовать SQLAlchemy ORM для:
- datasets;
- ingestion_runs;
- parser_registry;
- schema_versions;
- parser_runs;
- artifact registry;
- data_quality_reports;
- label_mapping_rules;
- preprocessing_artifacts.

Использовать SQLAlchemy Core для:
- массового insert/upsert dataset_files;
- повторного ingestion;
- обновления last_seen_at;
- batch update statuses.

Практическое правило:
- ORM = читаемый бизнес-код;
- Core = высокая производительность для массовых операций.

6. MODELS REQUIREMENTS
================================================================================

Общие требования к ORM models:
- Declarative Base with naming_convention;
- type annotations через SQLAlchemy 2.x Mapped[];
- constraints совпадают с PostgreSQL schema contract;
- relationship использовать там, где нужна traceability;
- JSONB поля использовать для metadata_json/raw details;
- nullable=True только там, где значение реально может отсутствовать.

Naming convention:
- ix_%(column_0_label)s
- uq_%(table_name)s_%(column_0_name)s
- ck_%(table_name)s_%(constraint_name)s
- fk_%(table_name)s_%(column_0_name)s_%(referred_table_name)s
- pk_%(table_name)s

8. SERVICE LAYER
================================================================================

SQLAlchemy должен использоваться через service layer, а не напрямую из parser code.

Рекомендуемые services:

CatalogIngestionService:
- сканирует directories;
- считает file metadata/hash;
- вызывает DatasetRepository и DatasetFileRepository;
- обновляет ingestion_runs.

ParserRunService:
- берет files READY_FOR_PARSING;
- получает parser via ParserRepository;
- создает parser_run;
- передает parser output в ArtifactRegistryService.

ArtifactRegistryService:
- регистрирует normalized/feature/model-ready/preprocessing artifacts;
- проверяет role/branch compatibility;
- фиксирует row_count and schema_version.

TraceabilityService:
- строит цепочку model_ready -> feature -> normalized -> parser_run -> file -> dataset.

LeakageGuardService:
- проверяет, что TEST не участвует в preprocessing fit;
- проверяет, что X artifacts не содержат label/source leakage columns;
- сохраняет data_quality_reports.

9. ALEMBIC REQUIREMENTS
================================================================================

Alembic обязателен.

Правила:
- первая migration создает всю Stage Two catalog schema;
- новые изменения только через новые revisions;
- не редактировать migration, если она уже применялась в shared/dev database;
- autogenerate можно использовать, но migration нужно проверять вручную;
- migration должна содержать indexes, unique constraints, check constraints and foreign keys.

Команды:

alembic init scripts/db/migrations
alembic revision --autogenerate -m "create stage two catalog schema"
alembic upgrade head
alembic downgrade -1

10. BULK UPSERT DATASET_FILES
================================================================================

Нужен PostgreSQL ON CONFLICT по UNIQUE(dataset_id, file_path).

Поведение:
- новый файл -> INSERT status='REGISTERED';
- файл уже есть и hash не изменился -> update last_seen_at;
- файл уже есть и hash изменился -> update hash, size, modified_at, status='CHANGED';
- пустой файл -> status='EMPTY_FILE';
- unsupported format -> status='UNSUPPORTED_FORMAT';
- ошибка -> status='FAILED', error_message заполнен.

11. NULL POLICY В SQLALCHEMY MODELS
================================================================================

Если значение отсутствует в датасете, записывать Python None.
SQLAlchemy должен передавать это как SQL NULL.

Не использовать:
- пустую строку вместо None;
- 0 вместо отсутствующего numeric value;
- False вместо отсутствующего boolean value;
- 'unknown' вместо NULL для технических колонок.

Допустимое исключение:
- label_status='unlabeled' и label_source='none' как явный статус label resolver;
- label_family='unknown' только если это согласовано в label schema.

12. DATA LEAKAGE GUARDS НА УРОВНЕ DB LAYER
================================================================================

DB layer должен помогать контролировать leakage:
- role обязателен в split-bearing tables;
- branch обязателен в branch-bearing tables;
- preprocessing_artifacts.fitted_on_role должен быть только TRAIN;
- model_ready_artifacts должен ссылаться на preprocessing_artifact_id;
- data_quality_reports должен фиксировать leakage check;
- репозиторий не должен создавать model_ready SUCCESS, если leakage check failed.

13. CODE STYLE REQUIREMENTS
================================================================================

Для каждого нового Python файла:
- module docstring;
- type hints;
- публичные классы с docstring;
- публичные методы с docstring;
- короткие комментарии на нетривиальную логику;
- нет hardcoded credentials;
- нет чтения больших raw files в DB foundation tasks.

ООП применять для:
- repositories;
- services;
- parser abstractions;
- writers;
- quality checkers.

Функциональный стиль допустим для:
- small pure helpers;
- path normalization;
- hash calculation;
- SQL string templates for DuckDB.

15. ACCEPTANCE CRITERIA
================================================================================

SQLAlchemy layer считается готовым, если:
- DATABASE_URL читается из .env;
- engine/session/session_scope работают;
- Alembic migration создает все catalog tables;
- ORM models покрывают все таблицы;
- repositories покрывают основные операции;
- bulk upsert dataset_files реализован через Core;
- parser/artifact/quality lifecycle работает через services;
- constraints защищают role/branch/status values;
- NULL policy соблюдается;
- TEST не может стать fitted_on_role for preprocessing artifacts;
- traceability service возвращает цепочку до raw file.
