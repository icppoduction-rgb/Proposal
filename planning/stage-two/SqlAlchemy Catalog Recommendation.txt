ФИНАЛЬНАЯ РЕКОМЕНДАЦИЯ ПО ИСПОЛЬЗОВАНИЮ SQLALCHEMY ДЛЯ POSTGRESQL CATALOG
Проект: Proposal — Behaviour-driven hybrid learning for data exfiltration detection
Этап: Stage Two — Data Normalization
Файл: final_sqlalchemy_catalog_recommendation.txt


================================================================================
1. КРАТКИЙ ВЫВОД
================================================================================

Использовать SQLAlchemy в проекте — правильное решение.

Рекомендуемая позиция:

SQLAlchemy нужно использовать как основной Python-слой доступа к PostgreSQL catalog,
но не как инструмент хранения больших данных.

PostgreSQL в проекте должен оставаться управляющим catalog/pipeline-control слоем.
Он должен хранить metadata, статусы, связи, версии parser-ов, версии схем,
пути к Parquet artifacts, quality reports и контроль TRAIN / VALIDATION / TEST.

Большие данные должны оставаться вне PostgreSQL:

- raw datasets — в raw filesystem layer;
- normalized events — в Parquet;
- feature tables — в Parquet;
- model-ready tabular artifacts — в Parquet;
- sequence windows для LSTM — в NPZ / Parquet / similar artifact format;
- аналитические SQL-запросы по большим данным — через DuckDB поверх Parquet.

Итоговая рекомендация:

    SQLAlchemy + Alembic + PostgreSQL catalog = да.
    SQLAlchemy для хранения normalized events/features = нет.
    SQLAlchemy для catalog ingestion, parser runs и artifact registry = да.


================================================================================
2. ПОЧЕМУ SQLALCHEMY ПОДХОДИТ ДЛЯ ЭТОГО ПРОЕКТА
================================================================================

SQLAlchemy хорошо подходит, потому что Stage Two требует не просто создать таблицы,
а постоянно взаимодействовать с catalog из Python pipeline.

В проекте нужно будет программно:

1. Создавать записи о датасетах.
2. Регистрировать raw-файлы.
3. Считать и сохранять file hash.
4. Фиксировать role: TRAIN / VALIDATION / TEST / EXPERIMENTS.
5. Фиксировать branch: dns / host / network / hybrid.
6. Назначать parser.
7. Создавать parser_runs.
8. Обновлять статусы обработки.
9. Регистрировать normalized Parquet artifacts.
10. Регистрировать feature Parquet artifacts.
11. Регистрировать model-ready artifacts.
12. Сохранять data quality reports.
13. Проверять data leakage conditions.
14. Обеспечивать traceability от model-ready artifact до raw-файла.

Писать все эти операции вручную через raw SQL можно, но это быстро станет
неудобным и рискованным. SQLAlchemy позволяет централизовать работу с БД,
сделать код чище и уменьшить вероятность ошибок при изменении схемы.


================================================================================
3. КАК ИМЕННО ИСПОЛЬЗОВАТЬ SQLALCHEMY
================================================================================

Рекомендуется использовать два режима SQLAlchemy:

1. SQLAlchemy ORM
   Для обычной работы с catalog entities:
   - datasets;
   - ingestion_runs;
   - dataset_files;
   - parser_registry;
   - parser_runs;
   - schema_versions;
   - normalized_artifacts;
   - feature_artifacts;
   - model_ready_artifacts;
   - data_quality_reports.

2. SQLAlchemy Core
   Для bulk operations:
   - массовая регистрация сотен тысяч raw-файлов;
   - batch insert dataset_files;
   - upsert при повторном catalog ingestion;
   - быстрые update статусов;
   - массовая запись ingestion summaries.

Практическое правило:

    ORM использовать для читаемого бизнес-кода.
    Core использовать для больших batch-операций.


================================================================================
4. ОБЯЗАТЕЛЬНО ИСПОЛЬЗОВАТЬ ALEMBIC
================================================================================

SQLAlchemy отвечает за работу с БД из Python.
Alembic отвечает за миграции схемы БД.

Рекомендация:

    Использовать SQLAlchemy вместе с Alembic.

Почему Alembic нужен:

1. Схема catalog будет развиваться.
2. Таблицы будут дополняться новыми полями.
3. Понадобятся новые индексы.
4. Понадобятся новые CHECK / UNIQUE constraints.
5. Нужно будет воспроизводимо разворачивать БД на другой машине.
6. Нужно будет откатывать изменения при ошибках.
7. SQL-файл 001_create_catalog_schema.sql подходит для старта, но неудобен
   для долгосрочного сопровождения.

Правильный подход:

- начальную схему можно зафиксировать в первой migration;
- дальше любые изменения делать через Alembic revision;
- не редактировать вручную уже применённые migration-файлы.

================================================================================
8. КАКИЕ ТАБЛИЦЫ ОСТАВИТЬ В CATALOG SCHEMA
================================================================================

Финальная catalog schema должна включать минимум 10 таблиц:

1. datasets
2. ingestion_runs
3. dataset_files
4. parser_registry
5. parser_runs
6. schema_versions
7. normalized_artifacts
8. feature_artifacts
9. model_ready_artifacts
10. data_quality_reports

Эта структура достаточна для Stage Two.

Таблица datasets:
- хранит список датасетов;
- фиксирует branch;
- фиксирует role;
- позволяет не дублировать dataset_name везде.

Таблица ingestion_runs:
- фиксирует каждый запуск сканирования raw datasets;
- хранит root_path, started_at, finished_at, status;
- хранит files_seen, files_new, files_existing, files_changed, files_failed.

Таблица dataset_files:
- самая важная таблица raw layer;
- каждая запись = один raw-файл;
- хранит path, relative_path, file hash, size, format, role, branch;
- служит входом для parser routing.

Таблица parser_registry:
- хранит доступные parser-ы;
- связывает branch + source_format + role с parser_name;
- позволяет управлять parser routing через catalog.

Таблица parser_runs:
- фиксирует попытки parsing по каждому файлу;
- хранит parser_name, parser_version, rows_read, rows_parsed, rows_failed;
- хранит output_parquet_path и error_message.

Таблица schema_versions:
- хранит версии normalized/features/model-ready схем;
- нужна для воспроизводимости и совместимости artifacts.

Таблица normalized_artifacts:
- хранит ссылки на normalized Parquet;
- связывает raw file -> parser run -> normalized artifact.

Таблица feature_artifacts:
- хранит ссылки на feature Parquet;
- фиксирует feature_group, row_count, feature_count.

Таблица model_ready_artifacts:
- хранит финальные X/y/sequences/split_index/preprocessing_object artifacts;
- фиксирует role, branch, sample_count, label_distribution.

Таблица data_quality_reports:
- хранит результаты проверок качества;
- нужна для parser reports, normalization reports, leakage checks и schema mismatch reports.


================================================================================
9. ЧТО НЕ НУЖНО ДЕЛАТЬ ЧЕРЕЗ SQLALCHEMY
================================================================================

SQLAlchemy не должен использоваться для:

1. Чтения PCAP / PCAPNG / CAP.
2. Чтения BSON event streams.
3. Потоковой обработки больших TXT syscall traces.
4. Загрузки всех JSON Lines events в PostgreSQL.
5. Хранения normalized events как строк PostgreSQL.
6. Хранения feature matrix в PostgreSQL.
7. Хранения sequence windows для LSTM в PostgreSQL.
8. Массовой аналитики по Parquet.
9. Feature engineering по миллионам событий внутри PostgreSQL.
10. Training / inference данных.

Для этих задач использовать:

- PyArrow / Polars / pandas — чтение и запись Parquet;
- DuckDB — SQL-запросы по Parquet;
- Scapy / tshark / pyshark — packet parsing;
- bson / pymongo bson tools — BSON parsing;
- streaming readers — большие text/json/jsonl/log/txt источники.

================================================================================

Правильная схема:

    ↓

    ↓
PostgreSQL catalog через SQLAlchemy
    ↓

    ↓

    ↓

    ↓

    ↓
FEATURE EXTRACTION
    ↓
feature_artifacts регистрируются через SQLAlchemy
    ↓
MODEL-READY DATASETS
    ↓
model_ready_artifacts регистрируются через SQLAlchemy
    ↓
DATA QUALITY REPORTS
    ↓
data_quality_reports сохраняются через SQLAlchemy

Шаг 1. Зафиксировать database configuration

Создать:

Задача:

- валидировать наличие переменной;
- не хранить credentials в коде.

Шаг 2. Создать SQLAlchemy session layer

Создать:

scripts/db/session.py

Задача:
- создать engine;
- создать sessionmaker;
- дать context manager для работы с транзакциями.

Шаг 3. Описать модели catalog tables

Создать модели для:

- Dataset;
- IngestionRun;
- DatasetFile;
- ParserRegistry;
- ParserRun;
- SchemaVersion;
- NormalizedArtifact;
- FeatureArtifact;
- ModelReadyArtifact;
- DataQualityReport.

Шаг 4. Создать migration

Лучший вариант:

alembic revision --autogenerate -m "create catalog schema"

Затем вручную проверить migration.

Шаг 5. Применить migration

Через Alembic:

alembic upgrade head

Шаг 6. Реализовать repository layer

Создать repository-классы:

- DatasetRepository;
- IngestionRepository;
- DatasetFileRepository;
- ParserRepository;
- ArtifactRepository;
- DataQualityRepository.

Шаг 7. Реализовать smoke test

Проверить:

1. Подключение к PostgreSQL.
2. Создание test dataset.
3. Создание ingestion_run.
4. Создание dataset_file.
5. Проверка UNIQUE constraints.
6. Проверка CHECK constraints.
7. Rollback при ошибке.

Шаг 8. Только после этого переходить к catalog ingestion

Catalog ingestion должен:

- сканировать raw dataset folders;
- определять dataset_name;
- определять branch;
- определять role;
- определять source_format;
- считать file_size_bytes;
- считать sha256 hash;
- записывать dataset_files;
- обновлять ingestion_runs;
- не читать содержимое больших файлов;
- не изменять raw-файлы.


================================================================================
12. РЕКОМЕНДУЕМЫЕ РЕЖИМЫ РАБОТЫ С ТРАНЗАКЦИЯМИ
================================================================================

Для маленьких операций:

- одна транзакция на логическую операцию;
- commit после успешной операции;
- rollback при ошибке.

Для catalog ingestion:

- ingestion_run создается в начале со status = RUNNING;
- файлы вставляются batch-ами;
- при частичной ошибке run получает status = PARTIAL_SUCCESS;
- при полной ошибке run получает status = FAILED;
- при полном успехе run получает status = SUCCESS.

Не рекомендуется:

- держать одну огромную транзакцию на сотни тысяч файлов;
- делать commit после каждого отдельного файла;
- игнорировать IntegrityError;
- молча пропускать файлы без записи error_message.


================================================================================
13. BULK INSERT / UPSERT РЕКОМЕНДАЦИЯ
================================================================================

Так как в проекте много файлов, особенно в host datasets, обычный ORM insert по одному
файлу будет слишком медленным.

Рекомендация:

1. Для небольших таблиц использовать ORM:
   - datasets;
   - parser_registry;
   - schema_versions.

2. Для dataset_files использовать SQLAlchemy Core bulk insert.

3. Для повторного ingestion использовать PostgreSQL ON CONFLICT:

Уникальность:

    UNIQUE(dataset_id, file_path)

Поведение:

- если файл новый — insert;
- если файл уже есть и hash не изменился — обновить last_seen_at;
- если файл уже есть и hash изменился — обновить file_hash, file_size_bytes,
  modified_at, status = REGISTERED или CHANGED;
- если файл пустой — status = EMPTY_FILE;
- если не удалось обработать — status = FAILED и error_message.


================================================================================
14. КОНТРОЛЬ DATA LEAKAGE
================================================================================

SQLAlchemy должен помогать контролировать data leakage через catalog.

Обязательные правила:

1. role должен быть обязательным на уровне datasets, dataset_files,
   normalized_artifacts, feature_artifacts, model_ready_artifacts.

2. CHECK constraints должны ограничивать role:
   TRAIN / VALIDATION / TEST / EXPERIMENTS.

3. branch должен быть обязательным почти во всех ключевых таблицах:
   dns / host / network / hybrid.

4. TEST artifacts нельзя использовать при fit scaler, encoder, feature selector
   или модели.

5. Если preprocessing_object сохраняется в model_ready_artifacts, он должен быть
   связан с TRAIN-only fit.

6. Любое изменение role у dataset после создания artifacts должно требовать
   пересборки downstream layers.

7. Не смешивать DNS и Host без явного branch/modality.


================================================================================
15. TRACEABILITY REQUIREMENTS
================================================================================

Catalog должен позволять пройти цепочку назад:

model_ready_artifacts.artifact_path
    ↓
feature_artifacts.feature_path
    ↓
normalized_artifacts.normalized_path
    ↓
parser_runs.file_id
    ↓
dataset_files.file_path
    ↓
datasets.name

Для этого важно:

1. normalized_artifacts должен ссылаться на file_id и parser_run_id.
2. feature_artifacts должен ссылаться на normalized_artifact_id, если возможно.
3. model_ready_artifacts должен ссылаться на feature_artifact_id, если возможно.
4. dataset_files должен хранить file_hash.
5. parser_runs должен хранить parser_version.
6. artifacts должны хранить schema_version.
7. quality reports должны ссылаться на artifact_type + artifact_id.

16. КОНТРОЛЬ КАЧЕСТВА
================================================================================

В catalog нужно сохранять summary quality checks:

- rows_total;
- rows_valid;
- rows_failed;
- missing_values_count;
- duplicate_rows_count;
- schema_mismatch_count;
- label_distribution;
- timestamp_coverage;
- report_path.

Quality reports должны создаваться для:

1. dataset_file;
2. parser_run;
3. normalized_artifact;
4. feature_artifact;
5. model_ready_artifact.

Минимальные проверки:

- file exists;
- file size > 0;
- hash calculated;
- role exists;
- branch exists;
- source_format exists;
- parser_name exists where needed;
- parser_version exists where needed;
- schema_version exists where needed;
- row_count exists for artifacts;
- timestamp coverage calculated where possible;
- label coverage calculated where possible.

17. ЧТО СДЕЛАТЬ ПРЯМО СЕЙЧАС
================================================================================

Финальная рекомендация для текущего момента:

1. Оставить текущую PostgreSQL catalog schema как основу.
2. Добавить SQLAlchemy как Python access layer.
3. Добавить Alembic как migration layer.
4. Не переносить normalized/events/features в PostgreSQL.
5. Реализовать сначала только DB infrastructure:
   - config.py;
   - session.py;
   - models;
   - initial migration;
   - repository skeleton;
   - smoke test.
6. После успешной проверки перейти к catalog ingestion.

Не начинать пока:

- parser routing;
- parser implementations;
- Parquet normalization;
- feature extraction;
- model training;
- SHAP;
- LSTM sequence windows.

Причина:
Сначала catalog schema и DB access layer должны быть стабильными. Иначе следующие
этапы будут строиться на нестабильной основе.

================================================================================
19. ФИНАЛЬНАЯ ТЕХНИЧЕСКАЯ ПОЗИЦИЯ
================================================================================

Правильное решение для проекта:

    PostgreSQL — catalog metadata and pipeline control.
    SQLAlchemy — Python access layer to PostgreSQL.
    Alembic — controlled database migrations.
    Parquet — storage for normalized/features/model-ready big data.
    DuckDB — analytics over Parquet.
    Raw filesystem — immutable source datasets.

SQLAlchemy использовать обязательно имеет смысл, потому что проект будет активно
создавать, обновлять и проверять metadata на каждом шаге Stage Two.

Но важно не нарушить архитектурное разделение:

    SQLAlchemy управляет catalog.
    SQLAlchemy не управляет большими ML datasets.

Такой подход соответствует требованиям Stage Two:
- raw-файлы остаются неизменными;
- traceability сохраняется;
- TRAIN / VALIDATION / TEST не смешиваются;
- parser/version/schema metadata фиксируются;
- Parquet остается основным форматом больших данных;
- PostgreSQL не превращается в хранилище всех событий;
- проект остается переносимым и воспроизводимым.
