Ключевые выводы для реализации:

1. PostgreSQL в проекте должен быть catalog / pipeline-control слоем, а не хранилищем больших данных.
2. Большие данные должны оставаться вне PostgreSQL:
   - raw datasets — в raw filesystem layer;
   - normalized events — в Parquet;
   - feature tables — в Parquet;
   - model-ready artifacts — в Parquet / NPZ;
   - аналитика по Parquet — через DuckDB.
3. PostgreSQL должен хранить metadata, статусы, связи, версии parser-ов, версии схем, пути к artifacts, quality reports и контроль TRAIN / VALIDATION / TEST.
4. SQLAlchemy нужно использовать как Python access layer к PostgreSQL catalog.
5. Alembic нужно использовать как migration layer.
6. SQLAlchemy ORM использовать для обычной работы с сущностями catalog.
7. SQLAlchemy Core использовать для bulk insert / upsert, особенно для dataset_files.
8. Текущая большая задача должна быть разбита на небольшие логически завершенные задачи.
9. На этом этапе нельзя реализовывать parser routing, parser implementations, Parquet normalization, feature extraction, model training, SHAP и LSTM sequence windows.
10. Главная цель текущего набора задач — получить стабильный DB foundation для последующего catalog ingestion.

Обязательные таблицы catalog schema:
1. datasets
2. ingestion_runs
3. dataset_files
4. parser_registry
5. parser_runs
6. schema_versions
7. normalized_artifacts
8. feature_artifacts
9. model_ready_artifacts
10. data_quality_reports

Обязательные architectural constraints:
- raw-файлы не изменять;
- пути к artifacts хранить как относительные пути от PATH_DATA_STORAGE там, где это возможно;
- role должен быть явно ограничен значениями TRAIN / VALIDATION / TEST / EXPERIMENTS;
- branch должен быть явно ограничен значениями dns / host / network / hybrid;
- TEST нельзя использовать для обучения scaler, encoder, feature selector, модели или настройки threshold;
- traceability должна позволять пройти цепочку:
  model_ready_artifacts -> feature_artifacts -> normalized_artifacts -> parser_runs -> dataset_files -> datasets.

1. ОБЩИЕ ТРЕБОВАНИЯ К КОДУ ДЛЯ ВСЕХ ЗАДАЧ
================================================================================

Эти требования применяются к каждой задаче ниже.

1. Код должен быть простым, читаемым и поддерживаемым.
2. Каждый новый Python-модуль должен иметь module docstring с кратким назначением файла.
3. Каждый публичный класс должен иметь docstring: что представляет класс и где используется.
4. Каждый публичный метод и функция должны иметь docstring: входные параметры, результат, побочные эффекты.
5. Для нетривиальных участков логики нужны короткие комментарии в коде.
6. Не добавлять комментарии, которые просто повторяют очевидный код.
7. Использовать type hints для аргументов и возвращаемых значений.
8. Не хранить реальные credentials в коде, .env.example или миграциях.
9. Не коммитить .env.
10. Не читать содержимое больших raw-файлов в задачах DB foundation.
11. Не создавать normalized Parquet artifacts в этих задачах.
12. Не смешивать DNS и Host логику без явного поля branch.
13. Не смешивать TRAIN / VALIDATION / TEST.
14. Все изменения должны проходить базовые проверки:
    - python -m compileall manage.py scripts
    - git diff --check
15. Если в проекте есть тестовый runner, запускать его после задач, где добавлены тесты.
16. После выполнения каждой задачи нужно сформировать два Markdown-отчета: русский и английский.
   Обязательный шаблон пути: PATH_REPORT/ru|en/stage-two/Task<number>(<название задачи>).md.
17. Отчеты сохранять в:
    - PATH_REPORT/ru/stage-two/Task<number>(<название задачи>).md
    - PATH_REPORT/en/stage-two/Task<number>(<name task>).md
18. Если в названии задачи есть символы, недопустимые для имени файла, например /, \, :, *, ?, ", <, >, |, заменить их на дефис.
19. Каждый отчет должен содержать: цель задачи, выполненные изменения, измененные файлы, команды проверки, результат проверок, git commit message, статус git push, проблемы/ограничения, следующий шаг.
20. Отчеты должны создаваться до команд git add / git commit / git push, чтобы они попали в коммит задачи.

--------------------------------------------------------------------------------
ЗАДАЧА 13. Создать initial Alembic migration для 10 catalog tables
--------------------------------------------------------------------------------

Цель:
Создать первую миграцию, которая воспроизводимо создает PostgreSQL catalog schema.

Что сделать:
1. Создать revision в scripts/db/migrations/versions/.
2. Назвать migration логически, например:
   - 001_create_catalog_schema.py
3. Migration должна создавать 10 таблиц:
   - datasets
   - ingestion_runs
   - dataset_files
   - parser_registry
   - parser_runs
   - schema_versions
   - normalized_artifacts
   - feature_artifacts
   - model_ready_artifacts
   - data_quality_reports
4. Migration должна создавать CHECK constraints.
5. Migration должна создавать UNIQUE constraints.
6. Migration должна создавать indexes.
7. Migration должна иметь downgrade(), который удаляет таблицы в корректном порядке зависимостей.
8. Вручную проверить autogenerate output перед коммитом.
9. Не использовать Base.metadata.create_all() вместо Alembic migration.

Acceptance criteria:
- Есть initial migration для catalog schema.
- upgrade() создает 10 обязательных таблиц.
- downgrade() удаляет таблицы без нарушения FK order.
- Constraints и indexes включены.
- python -m compileall manage.py scripts проходит без ошибок.
- git diff --check проходит без ошибок.


Отчет после выполнения:
1. Создать русский отчет:

2. Создать английский отчет:
   PATH_REPORT/en/stage-two/Task13(Create an initial Alembic migration for 10 catalog tables).md
3. В каждом отчете указать:
   - номер и название задачи;
   - цель задачи;
   - что было изменено;
   - список измененных/созданных файлов;

   - commit message из этой задачи;
   - результат git push origin dev;
   - проблемы, ограничения или TODO, если есть;
   - следующий рекомендуемый шаг.
4. Отчеты должны быть созданы до git add ., чтобы попасть в commit этой задачи.
