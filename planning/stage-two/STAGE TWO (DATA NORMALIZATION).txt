1. НАЗНАЧЕНИЕ ДОКУМЕНТА
================================================================================

Документ описывает полную реализацию второго этапа проекта: Data Normalization.
Этап должен перевести результаты Stage One от инвентаризации и анализа датасетов
к управляемому нормализованному слою данных, пригодному для feature engineering,
sequence modelling, ML/DL training, validation, testing и explainability.

Ключевое решение:
- raw-файлы остаются неизменными;
- PostgreSQL хранит только catalog / metadata / pipeline-control;
- Parquet хранит normalized events, feature tables и model-ready artifacts;
- DuckDB используется для аналитических SQL-запросов по Parquet;
- SQLAlchemy используется как Python DB access layer к PostgreSQL catalog;
- Alembic используется для воспроизводимых миграций catalog schema;
- TRAIN, VALIDATION и TEST разделяются физически, логически и на уровне constraints;
- если в датасете нет нужного значения, в normalized/schema/artifact колонку записывается NULL;
- нестандартные поля не теряются, а сохраняются в raw_fields_json, features_json или metadata_json.

4. ФИНАЛЬНАЯ АРХИТЕКТУРА ДАННЫХ
================================================================================

Общий pipeline:

RAW DATASETS
    -> CATALOG INGESTION
    -> POSTGRESQL CATALOG
    -> PARSER ROUTING
    -> NORMALIZED EVENTS
    -> PARQUET NORMALIZED LAYER
    -> FEATURE EXTRACTION
    -> PARQUET FEATURE LAYER
    -> MODEL-READY ARTIFACTS
    -> DUCKDB QUALITY / ANALYTICS
    -> TRAIN / VALIDATION / TEST ML/DL PIPELINE

Распределение ответственности:

1. Raw filesystem layer
   - хранит исходные файлы;
   - файлы не изменяются;
   - для каждого файла считается hash;
   - путь, размер, формат, роль и hash регистрируются в PostgreSQL.

2. PostgreSQL catalog
   - хранит datasets, files, parser runs, schema versions, artifact registry;
   - не хранит большие normalized events и feature matrices;
   - управляет traceability и статусами pipeline.

3. Parquet
   - хранит большие данные: normalized events, features, model-ready tabular data;
   - partitioning выполняется по branch, role, modality, dataset_slug и schema_version.

4. DuckDB
   - выполняет SQL-запросы поверх Parquet;
   - используется для quality checks, split checks, row counts, schema validation,
     aggregation previews и аналитических выборок;
   - не заменяет PostgreSQL catalog.

5. SQLAlchemy + Alembic
   - SQLAlchemy ORM используется для обычной работы с catalog entities;
   - SQLAlchemy Core используется для bulk insert/upsert dataset_files;
   - Alembic управляет schema migrations.

6. DATASET SCOPE И РОЛИ
================================================================================

DNS branch:

TRAIN:
- CIC-Bell-DNS-EXF-2021: attack-class DNS exfiltration/tunneling patterns.
- CIC-Bell-DNS-2021: benign DNS baseline.

VALIDATION:
- split CIC-Bell-DNS-2021: false positive control and threshold validation.

TEST:
- Mendeley DNS Exfiltration Dataset: independent generalization test.

Host branch:

TRAIN:
- ADFA IDS: HIDS baseline, syscall traces.
- LID-DS 2021: main sequence source for syscall/API modelling.
- Maintainable Log Dataset: enterprise logs and multi-stage behaviour.

VALIDATION:
- LID-DS 2019: cross-version validation.
- LANL Dataset: user-host/auth/lateral movement validation.
- Windows Event Log / OTRF Security Datasets: SOC-oriented Windows/Sysmon validation.

TEST:
- Unified Host + Network / LANL: final hybrid host+network test.
- ISOT Cloud IDS: cloud-like portability test.
- Dynamic Malware Analysis Dataset: malware-driven host behaviour test.

Правила:
- TEST нельзя использовать для fit scaler, encoder, imputer, feature selector,
  threshold или модели;
- labels не являются input features;
- filename, source_file, dataset_role, scenario_name не должны попадать в X_train,
  если они напрямую кодируют класс;
- отсутствие label не означает benign: label_binary должен быть NULL.

7. ФОРМАТЫ И PARSER STRATEGY
================================================================================

DNS formats:

1. DNS TRAIN csv
   - частично поддержан;
   - содержит domain-list и DNS/domain feature tables;
   - label часто берется из имени файла;
   - нужен schema-aware CSV parser.

2. DNS TRAIN pcap
   - нужен custom packet parser;
   - извлекаются DNS packet/query/response/flow summaries.

3. DNS TRAIN pcap.csv
   - готов для feature extraction;
   - содержит табличные производные packet/DNS поля.

4. DNS VALIDATION pcap
   - нужен packet parser;
   - label можно вывести из имени файла attack/benign.

5. DNS VALIDATION txt
   - domain-list;
   - подходит для lexical/domain features;
   - unknown class не использовать как supervised class без явного mapping.

6. DNS TEST csv
   - крупный headerless CSV;
   - нужна positional 22-column schema;
   - TEST-only.

Host formats:

1. Host TRAIN csv
   - system events, process_id, path, sys_call, event_id, attack categories, label;
   - нужен parser с поддержкой основной 9-column схемы и служебных CSV.

2. Host TRAIN auth.log / syslog / mail / raw logs
   - mixed raw syslog + JSON-lines;
   - нужен line-oriented parser с ветвлением по структуре строки.

3. Host TRAIN Metricbeat logs: cpu.log, diskio.log, memory.log, filesystem.log,
   fsstat.log, network.log, process.log, service.log, socket.summary.log, uptime.log
   - JSON-lines metrics;
   - нормализуются в host metric events.

4. Host TRAIN ghc / sc / txt traces
   - syscall/API/trace-like streams;
   - нужны streaming parsers и event_order support.

5. Host TRAIN json / json-1 / log variants
   - mixed JSON/JSON-lines/log wrappers;
   - parser должен сохранять raw_fields_json.

6. Host VALIDATION cap/pcap/pcapng
   - network packet captures;
   - parser должен строить packet/flow/DNS/SMB/LDAP/DCERPC summaries.

7. Host VALIDATION csv
   - scenario metadata;
   - использовать как label/context metadata, не как independent model feature.

8. Host TEST bson
   - sandbox process/API streams;
   - нужен BSON parser, descriptor mapping и event_order.

9. Host TEST netflow_day / wls_day / txt / log / json
   - использовать для TEST/inference/evaluation;
   - не применять для обучения.

- entity_id: string, NULL if missing
- event_type: string
- raw_event_name: string, NULL if missing
- modality: string, dns / syscall / eventlog / netflow / packet / metric / auth / process / file / sandbox
- host_name: string, NULL if missing

- process_name: string, NULL if missing

- dst_ip: string, NULL if missing

- dst_port: integer, NULL if missing

- qclass: string, NULL if missing
- ttl: integer, NULL if missing
- rcode: string, NULL if missing

- event_id: string, NULL if missing
- command_line: string, NULL if missing
- file_path: string, NULL if missing

9. DOMAIN-SPECIFIC NORMALIZATION RULES
================================================================================

9.1. DNS

Нормализовать:
- domain, query_domain, qtype, qclass, TTL, IP/ASN/enrichment, timestamp, label,
  source_file, dataset_role.

Сохранять в raw_fields_json:
- нестандартные CSV columns;
- WHOIS-derived fields;
- DNSBL provider fields;
- нераспознанные packet decoder fields.

Подготовить для features:
- domain length, subdomain length/depth, label count;
- TLD/SLD;
- entropy;
- TTL statistics;
- RR type distribution;
- query type distribution;
- RCODE/NXDOMAIN;
- inter-query intervals;
- query rate;
- unique subdomain ratio;
- amplification ratio.

9.2. Host syscall/API

Нормализовать:
- process, pid, syscall/API/method name, event_index, timestamp/relative time,
  args, direction, user_id, process_path, label.

Подготовить для features:
- syscall/API frequencies;
- 2-gram/3-gram;
- transition probabilities;
- trace length;
- unique syscall count;
- collection syscall counts;
- network syscall counts;
- sequence windows for LSTM.

9.3. Windows EventLog / Sysmon / WLS

Нормализовать:
- EventID, Channel, SourceName, Hostname, UserName, ProcessName,
  ParentProcessName, CommandLine, LogonType, SourceAddress, DestinationAddress,
  timestamp, label/context metadata.

Подготовить для features:
- EventID frequencies;
- logon success/failure ratio;
- parent-child process chains;
- command-line entropy;
- encoded PowerShell indicator;
- user-host interactions;
- SourceAddress/DestinationAddress counts.

9.4. NetFlow / packet / PCAP / CAP / PCAPNG

Нормализовать:
- packet timestamp, src/dst IP, src/dst port, protocol, packet size, TCP flags,
  DNS query/response fields, flow_id, label from metadata if available.

Не хранить в PostgreSQL:
- full packet payload;
- raw capture packet stream.

Хранить:
- raw capture остается в raw layer;
- packet/flow summaries сохраняются в Parquet;
- PostgreSQL хранит metadata and artifact paths.

9.5. BSON / sandbox telemetry

Нормализовать:
- descriptor id, event id, event name, category, process/thread context,
  relative time, args, command line, module path, file artifacts, external label.

Требование:
- сохранить порядок документов;
- сопоставить descriptor documents и event documents;
- неизвестные args сохранять в raw_fields_json.

9.6. Metricbeat/system metrics

Нормализовать:
- host, timestamp, metric type, CPU, memory, disk I/O, filesystem, network stats,
  process summary, service state.

Подготовить для features:
- rolling mean/max/std;
- burst score;
- baseline deviation;
- CPU/memory/disk pressure;
- service state changes;
- correlation with auth/process/network events.

10. PARQUET STORAGE CONTRACT
================================================================================

10.1. Normalized Parquet

Путь:

parquet/normalized/{branch}/{role}/{modality}/{dataset_slug}/schema={schema_version}/part-YYYYMMDD-HHMMSS-{run_id}.parquet

Примеры:

parquet/normalized/dns/TRAIN/dns_query/cic_bell_dns_exf_2021/schema=v1/part-000001.parquet
parquet/normalized/host/TRAIN/syscall/lid_ds_2021/schema=v1/part-000001.parquet
parquet/normalized/network/VALIDATION/packet/otrf_cap/schema=v1/part-000001.parquet

Рекомендации:
- compression: zstd или snappy;
- row group size: настроить после первых замеров;
- schema_version обязательно;
- row_count регистрировать в PostgreSQL;
- output artifacts append-only; не перезаписывать без нового parser_run_id.

10.2. Feature Parquet

Путь:

parquet/features/{feature_group}/{role}/{dataset_slug}/schema={feature_schema_version}/part-{run_id}.parquet

Feature groups:
- dns_features;
- host_syscall_features;
- host_eventlog_features;
- host_metrics_features;
- network_flow_features;
- hybrid_features;
- sequence_features.

Обязательные traceability columns:
- feature_uid;
- dataset_id;
- source_normalized_artifact_id;
- dataset_role;
- branch;
- feature_group;
- window_start;
- window_end;
- entity_type;
- entity_id;
- label_binary;
- label_family;
- label_status;
- raw_source_refs_json.

10.3. Model-ready artifacts

Путь:

parquet/model_ready/tabular/{branch}/{role}/schema={schema_version}/X_{role_lower}.parquet
parquet/model_ready/labels/{branch}/{role}/schema={schema_version}/y_{role_lower}.parquet
parquet/model_ready/sequences/{branch}/{role}/schema={schema_version}/{role_lower}_sequences.npz
parquet/model_ready/preprocessing/{branch}/schema={schema_version}/train_fitted_preprocessing.pkl
parquet/model_ready/split_index/{branch}/schema={schema_version}/split_index.parquet

Правила:
- X не должен содержать label columns, source_file, dataset_role, scenario_name;
- y хранится отдельно;
- preprocessing artifacts fit только на TRAIN;
- VALIDATION и TEST только transform;
- sequence windows должны иметь mapping к normalized event_uid или event_uid list.

================================================================================

DuckDB используется для SQL-проверок поверх Parquet.

Постоянная БД:
- duckdb/proposal_analytics.duckdb

SQL-файлы:
- duckdb/sql/create_views.sql
- duckdb/sql/quality_checks.sql
- duckdb/sql/leakage_checks.sql
- duckdb/sql/feature_preview.sql

Рекомендуемые views:

CREATE OR REPLACE VIEW normalized_dns_train AS
SELECT *
FROM read_parquet('${PATH_DATA_STORAGE}/parquet/normalized/dns/TRAIN/**/*.parquet');

CREATE OR REPLACE VIEW normalized_host_train AS
SELECT *
FROM read_parquet('${PATH_DATA_STORAGE}/parquet/normalized/host/TRAIN/**/*.parquet');

CREATE OR REPLACE VIEW feature_all AS
SELECT *
FROM read_parquet('${PATH_DATA_STORAGE}/parquet/features/**/*.parquet', union_by_name=true);

Примеры проверок:

-- количество строк по split
SELECT dataset_role, branch, COUNT(*) AS rows_count
FROM feature_all
GROUP BY dataset_role, branch;

-- missing values в ключевых полях
SELECT dataset_role, branch,
       SUM(CASE WHEN event_uid IS NULL THEN 1 ELSE 0 END) AS missing_event_uid,
       SUM(CASE WHEN dataset_role IS NULL THEN 1 ELSE 0 END) AS missing_role,
       SUM(CASE WHEN branch IS NULL THEN 1 ELSE 0 END) AS missing_branch
FROM read_parquet('${PATH_DATA_STORAGE}/parquet/normalized/**/*.parquet', union_by_name=true)
GROUP BY dataset_role, branch;

-- проверка, что TEST не попал в train model-ready features
SELECT COUNT(*) AS test_rows_in_train_artifact
FROM read_parquet('${PATH_DATA_STORAGE}/parquet/model_ready/tabular/*/TRAIN/**/*.parquet', union_by_name=true)
WHERE dataset_role = 'TEST';

13. DATA QUALITY CHECKS
================================================================================

Parser-level checks:
- файл существует;
- hash рассчитан;
- файл не изменился с момента catalog ingestion;
- формат соответствует parser_registry;
- parser_run status: RUNNING / SUCCESS / PARTIAL_SUCCESS / FAILED / SKIPPED;
- rows_read, rows_parsed, rows_failed сохранены.

Normalized-level checks:
- event_uid не NULL;
- dataset_id/file_id присутствуют;
- dataset_role входит в TRAIN/VALIDATION/TEST/EXPERIMENTS;
- branch входит в dns/host/network/hybrid;
- schema_version заполнен;
- timestamp или event_index присутствует;
- raw_fields_json заполнен для unmapped fields;
- label_status корректен.

Feature-level checks:
- feature_count > 0;
- нет label columns в X artifacts;
- нет source_file/scenario_name как model feature;
- feature schema одинаковая между TRAIN/VALIDATION/TEST, кроме допустимых NULL;
- categorical encoding fit только на TRAIN.

Model-ready checks:
- X_train/y_train aligned by sample_uid;
- X_validation/y_validation aligned;
- X_test/y_test aligned;
- preprocessing_object связан с TRAIN;
- TEST отсутствует в fit metadata;
- sequence windows имеют event_uid references.

14. LABEL RESOLVER CONTRACT
================================================================================

Canonical label fields:
- label_binary: 0 / 1 / NULL;
- label_family: benign / dns_exfiltration / malware / phishing / lateral_movement /
  privilege_escalation / unknown / NULL;
- label_subtype: concrete subtype or scenario;
- label_source: embedded_column / filename / scenario_metadata / external_label_file /
  ids_alert / ground_truth_csv / none;
- label_status: explicit_label / inferred_label / weak_label / partial_label /
  unlabeled / conflicting_label;
- label_confidence: float;
- label_mapping_rule_id: string.

Priority order:
1. embedded explicit label column;
2. official ground_truth file;
3. scenario metadata with clear time boundaries;
4. filename/class hint;
5. IDS alert or weak external signal;
6. no label -> label_binary=NULL, label_status=unlabeled.

Не делать:
- не считать отсутствие label как benign;
- не использовать TEST labels для training decisions;
- не использовать scenario_name as model feature;
- не объединять conflicting labels без отдельного статусного поля.

15. DATA LEAKAGE PREVENTION
================================================================================

Обязательные правила:

1. Физическое разделение:
   - parquet/normalized/{branch}/{role}/...
   - parquet/features/{feature_group}/{role}/...
   - parquet/model_ready/{artifact_type}/{branch}/{role}/...

2. Catalog constraints:
   - role CHECK in all split-bearing tables;
   - branch CHECK in all branch-bearing tables;
   - artifact role must match upstream artifact role.

3. Preprocessing:
   - fit scaler/encoder/imputer only on TRAIN;
   - transform VALIDATION and TEST using TRAIN-fitted objects;
   - store preprocessing_artifacts with fitted_on_role='TRAIN'.

4. Feature controls:
   - exclude label_binary, label_family, label_subtype, label_status from X;
   - exclude source_file, dataset_role, scenario_name if they encode labels;
   - exclude dataset_name if it separates classes too directly.

5. Quality checks:
   - generate data leakage report before model-ready artifacts are accepted;
   - block model_ready status SUCCESS if leakage check failed.

18. DEFINITION OF DONE
================================================================================

Stage Two считается реализованным, если:

1. PostgreSQL catalog schema развернута через Alembic.
2. SQLAlchemy DB layer работает через config/session/repositories.
3. Все raw-файлы зарегистрированы в dataset_files с hash, size, role, branch,
   source_format и status.
4. Parser registry позволяет выбрать parser для каждого поддержанного формата.
5. Parser runs фиксируют rows_read, rows_parsed, rows_failed, output path и errors.
6. Normalized events сохранены в Parquet и зарегистрированы в normalized_artifacts.
7. Feature artifacts зарегистрированы и физически разделены по TRAIN/VALIDATION/TEST.
8. Model-ready artifacts не содержат leakage columns в X.
9. TEST не использовался для fit preprocessing.
10. Missing values в исходных данных представлены как NULL.
11. raw_fields_json/features_json сохраняют нестандартные поля.
12. DuckDB queries позволяют проверить Parquet без загрузки данных в PostgreSQL.
13. Data quality и leakage reports созданы.
14. Traceability работает от model_ready artifact до raw file.
15. Код содержит type hints, docstrings, понятные комментарии и проходит compile checks.

19. ЧТО НЕ ВХОДИТ В STAGE TWO
================================================================================

Не выполнять в Stage Two:
- обучение финальных моделей;
- подбор гиперпараметров;
- финальную оценку модели;
- SHAP reports;
- окончательный feature selection;
- объединение всех данных в один CSV;
- загрузку всех normalized events в PostgreSQL;
- изменение raw datasets;
- удаление проблемных raw-файлов;
- использование TEST для training/preprocessing fit;
- хранение full packet payload в PostgreSQL;
- ручное исправление исходных файлов.

20. ФИНАЛЬНАЯ РЕКОМЕНДАЦИЯ
================================================================================

Использовать архитектуру:

PostgreSQL catalog + SQLAlchemy/Alembic + Parquet + DuckDB

Роль каждого компонента:
- PostgreSQL: metadata, catalog, statuses, traceability, control plane;
- SQLAlchemy: Python access layer for catalog;
- Alembic: reproducible schema migrations;
- Parquet: large normalized/features/model-ready data;
- DuckDB: analytical SQL over Parquet;
- raw filesystem: immutable source datasets.

Главное ограничение:
PostgreSQL не должен превращаться в хранилище больших событий или feature matrix.
Он должен управлять pipeline и хранить ссылки на artifacts.
