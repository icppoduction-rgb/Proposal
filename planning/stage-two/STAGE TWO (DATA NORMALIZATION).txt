ЭТАП 2. НОРМАЛИЗАЦИЯ ДАННЫХ ДЛЯ ОБУЧЕНИЯ И ТЕСТИРОВАНИЯ МОДЕЛИ

1. Цель этапа

Реализовать этап нормализации данных после анализа датасетов, выполненного на ЭТАПЕ 1.

Основная цель этапа — привести разнородные DNS, Host, Network, Syscall, EventLog, NetFlow, PCAP, BSON, JSON, CSV, LOG, TXT и другие данные к единому управляемому представлению без потери исходной информации.

На данном этапе необходимо:
- сохранить исходные данные без изменений;
- реализовать parser-ы для каждого поддерживаемого формата;
- преобразовать данные в нормализованную событийную структуру;
- сохранить нормализованные данные в Parquet;
- использовать PostgreSQL как каталог метаданных и контроль pipeline;
- использовать DuckDB для аналитических SQL-запросов по Parquet;
- подготовить основу для feature engineering, sequence modelling, обучения, валидации и тестирования ML/DL моделей.

Важно:
Этап 2 не должен уничтожать, перезаписывать или упрощать исходные данные с потерей информации. Все raw-файлы должны оставаться неизменными, а нормализованные данные должны ссылаться на исходный файл, parser, версию схемы и роль датасета.


# =======
2. Основные задачи

1. Зафиксировать архитектуру хранения данных:
   - PostgreSQL — каталог, метаданные, статусы обработки, связи между слоями;
   - Parquet — нормализованные события, признаки и model-ready таблицы;
   - DuckDB — аналитический SQL-доступ к Parquet.

2. Реализовать catalog ingestion:
   - просканировать raw datasets;
   - зарегистрировать все файлы в PostgreSQL;
   - сохранить путь, размер, hash, формат, роль и ветку датасета;
   - зафиксировать статус обработки каждого файла.

3. Реализовать parser routing:
   - определить parser по формату файла;
   - использовать отдельные parser strategy для сложных форматов;
   - фиксировать parser version;
   - сохранять ошибки обработки без удаления исходных данных.

4. Реализовать normalized event layer:
   - привести данные разных форматов к единой normalized event schema;
   - сохранить результат в Parquet;
   - зарегистрировать Parquet-артефакты в PostgreSQL.

5. Обеспечить сохранение данных без потерь:
   - сохранять ссылки на raw_file_path;
   - сохранять file_id и dataset_id;
   - сохранять parser_name, parser_version и schema_version;
   - сохранять raw_event_name;
   - сохранять features_json или raw_fields_json для полей, которые не вошли в стандартные колонки;
   - сохранять timestamp_source и label_source;
   - фиксировать количество прочитанных, обработанных и ошибочных строк.

6. Разделить данные по ролям:
   - TRAIN;
   - VALIDATION;
   - TEST;
   - EXPERIMENTS, если используется.

7. Исключить data leakage:
   - не смешивать TRAIN, VALIDATION и TEST;
   - не использовать TEST для обучения scaler, encoder, feature selector или модели;
   - не использовать статистику TEST для заполнения missing values;
   - не использовать TEST для настройки threshold.

8. Подготовить данные для feature engineering:
   - DNS features;
   - Host syscall/API features;
   - Windows EventLog/Sysmon features;
   - NetFlow/network features;
   - Metricbeat/system metrics;
   - hybrid host+network features;
   - sequence windows для LSTM.

9. Подготовить отчёты качества:
   - parsing report;
   - normalization report;
   - data quality report;
   - data leakage check report;
   - schema mismatch report.


# =======
3. Общая логика этапа

Этап нормализации должен выполняться после анализа датасетов.

Общая схема:

RAW DATASETS
    ↓
CATALOG INGESTION
    ↓
PARSER ROUTING
    ↓
NORMALIZED EVENTS
    ↓
PARQUET STORAGE
    ↓
FEATURE EXTRACTION
    ↓
MODEL-READY DATASETS
    ↓
TRAIN / VALIDATION / TEST

Ключевая идея:
Не нужно превращать все исходные файлы в один общий CSV, JSON или одну большую таблицу PostgreSQL.

Правильный подход:
- исходные файлы остаются в raw layer;
- parser извлекает данные из каждого формата;
- результат сохраняется в normalized event layer;
- большие нормализованные данные хранятся в Parquet;
- PostgreSQL хранит только каталог, метаданные, статусы, связи и ссылки на артефакты;
- DuckDB используется для запросов и аналитики по Parquet.


# =======
4. Архитектурное решение по хранению данных

4.1. PostgreSQL

PostgreSQL используется как центральная база метаданных.

В PostgreSQL нужно хранить:
- список датасетов;
- роли датасетов;
- список исходных файлов;
- формат каждого файла;
- размер файла;
- hash файла;
- путь к raw-файлу;
- статус обработки;
- parser_name;
- parser_version;
- schema_version;
- количество прочитанных строк/событий;
- количество успешно обработанных строк/событий;
- количество ошибок;
- путь к normalized Parquet;
- путь к feature Parquet;
- путь к model-ready artifacts;
- информацию о label_source;
- информацию о timestamp_source;
- отчёты об ошибках;
- результаты data quality checks;
- результаты model runs и метрики модели, если этап будет связан с экспериментами.

PostgreSQL не должен использоваться для хранения:
- всех raw PCAP packets;
- всех BSON event streams в исходном виде;
- всех syslog строк без нормализации;
- всех широких feature matrix;
- всех sequence windows;
- больших промежуточных batch-таблиц.

Назначение PostgreSQL:
PostgreSQL должен быть не хранилищем всех больших данных, а управляющим каталогом проекта.


# =======
4.2. Parquet

Parquet используется как основной формат хранения больших нормализованных данных.

В Parquet нужно хранить:
- normalized DNS events;
- normalized host events;
- normalized network events;
- normalized syscall/API events;
- parsed Windows EventLog/Sysmon events;
- parsed NetFlow events;
- parsed packet/flow summaries;
- DNS feature tables;
- host syscall feature tables;
- host eventlog feature tables;
- host metrics feature tables;
- network flow feature tables;
- hybrid feature tables;
- model-ready tabular datasets.

Преимущества Parquet:
- колонночное хранение;
- эффективное сжатие;
- быстрое чтение отдельных колонок;
- удобная интеграция с Python ML stack;
- удобная работа с pandas, Polars, PyArrow, DuckDB, scikit-learn, PyTorch/TensorFlow;
- подходит для больших датасетов;
- снижает нагрузку на PostgreSQL.


# =======
4.3. DuckDB

DuckDB используется как аналитический SQL-движок поверх Parquet.

DuckDB нужен для:
- SQL-запросов к Parquet без загрузки данных в PostgreSQL;
- проверки качества данных;
- агрегаций перед feature engineering;
- анализа распределений;
- проверки количества строк;
- проверки TRAIN/VALIDATION/TEST split;
- объединения нескольких Parquet-файлов;
- построения промежуточных аналитических выборок.

Пример использования:

SELECT *
FROM read_parquet('storage/normalized/dns/train/*.parquet')
WHERE event_type = 'dns_query';

SELECT dataset_role, source_format, COUNT(*)
FROM read_parquet('storage/features/host/*.parquet')
GROUP BY dataset_role, source_format;


# =======
5. Слои данных

5.1. Raw layer

Raw layer содержит исходные файлы датасетов.

Правила raw layer:
- исходные файлы не изменять;
- не удалять строки;
- не перезаписывать файлы;
- не исправлять raw-файлы вручную;
- не смешивать raw TRAIN, VALIDATION и TEST;
- хранить hash файла для контроля неизменности;
- в PostgreSQL хранить путь, размер, формат, роль и hash файла.

Назначение raw layer:
- обеспечить воспроизводимость;
- сохранить возможность повторной нормализации;
- сохранить доказательство, что данные не были изменены;
- обеспечить traceability от model-ready данных к исходному файлу.


# =======
5.2. Catalog layer

Catalog layer хранится в PostgreSQL.

Назначение:
- управлять всеми файлами и артефактами;
- отслеживать статус обработки;
- связывать raw, normalized, features и model-ready слои;
- хранить parser/version/schema metadata;
- хранить отчёты об ошибках и качестве.

Основные сущности:
- datasets;
- dataset_files;
- parser_runs;
- normalized_artifacts;
- feature_artifacts;
- model_ready_artifacts;
- data_quality_reports;
- model_runs.


# =======
5.3. Normalized layer

Normalized layer содержит данные, приведённые к единой событийной структуре.

Формат хранения:
- Parquet.

Назначение:
- унифицировать доступ к разным форматам;
- подготовить данные для feature extraction;
- сохранить исходный контекст события;
- обеспечить анализ последовательностей;
- обеспечить проверку качества данных.

Важно:
Если часть исходных полей не попадает в стандартные колонки normalized schema, их нужно сохранить в features_json, raw_fields_json или metadata_json, чтобы не потерять данные.


# =======
5.4. Feature layer

Feature layer содержит признаки, извлечённые из normalized events.

Примеры feature groups:
- dns_features;
- host_syscall_features;
- host_eventlog_features;
- host_metrics_features;
- network_flow_features;
- hybrid_features;
- sequence_features.

Формат хранения:
- Parquet.

Назначение:
- подготовить данные для ML/DL моделей;
- построить признаки для классификации;
- построить признаки для sequence modelling;
- подготовить данные для SHAP/explainability анализа.


# =======
5.5. Model-ready layer

Model-ready layer содержит финальные данные для моделей.

Примеры:
- X_train.parquet;
- y_train.parquet;
- X_validation.parquet;
- y_validation.parquet;
- X_test.parquet;
- y_test.parquet;
- train_sequences.npz;
- validation_sequences.npz;
- test_sequences.npz.

Правила:
- model-ready данные должны быть разделены по TRAIN, VALIDATION и TEST;
- scaler и encoder должны быть обучены только на TRAIN;
- TEST должен использоваться только для финальной оценки;
- sequence windows должны иметь связь с исходными normalized events.


# =======
6. Каноническая структура normalized_events

Для нормализованных событий рекомендуется использовать следующую базовую структуру:

- event_uid — уникальный идентификатор события;
- dataset_id — ссылка на датасет в PostgreSQL;
- file_id — ссылка на исходный файл в PostgreSQL;
- dataset_name — название датасета;
- dataset_role — TRAIN / VALIDATION / TEST / EXPERIMENTS;
- branch — dns / host / network / hybrid;
- source_format — csv / json / log / txt / pcap / pcapng / bson / netflow_day / wls_day / etc.;
- parser_name — имя parser-а;
- parser_version — версия parser-а;
- schema_version — версия normalized schema;
- timestamp — нормализованное время события;
- timestamp_source — исходное поле времени;
- timestamp_type — absolute / relative / event_order / missing;
- event_index — порядковый номер события, если timestamp отсутствует;
- entity_type — domain / host / ip / user / process / flow / packet / syscall / eventlog;
- entity_id — основной идентификатор сущности;
- event_type — тип события;
- raw_event_name — исходное имя события;
- modality — dns / syscall / eventlog / netflow / packet / metric / auth / process;
- features_json — структурированные признаки события;
- raw_fields_json — исходные поля, не вошедшие в стандартную схему;
- label — benign / malicious / unknown / attack type;
- label_source — column / filename / external_mapping / metadata / unknown;
- raw_file_path — путь к исходному файлу;
- normalized_path — путь к Parquet-файлу;
- created_at — время создания normalized записи.

Главное требование:
Ни одно важное поле из исходного файла не должно теряться. Если поле нельзя привести к стандартной колонке, оно должно быть сохранено в raw_fields_json или features_json.

# =======
9. Контроль сохранения данных без потерь

Чтобы исключить потерю данных, нужно соблюдать следующие правила:

1. Raw-файлы не изменять.
2. Для каждого файла вычислять hash до обработки.
3. Каждому raw-файлу назначать file_id.
4. Каждому normalized event назначать event_uid.
5. В каждом normalized event хранить file_id.
6. В каждом normalized event хранить raw_file_path.
7. В каждом normalized event хранить source_format.
8. В каждом normalized event хранить parser_name и parser_version.
9. В каждом normalized event хранить schema_version.
10. Все исходные поля, которые не вошли в основные колонки, сохранять в raw_fields_json.
11. Все извлечённые признаки события сохранять в features_json.
12. Для каждого parser run фиксировать rows_read, rows_parsed, rows_failed.
13. Ошибочные строки сохранять в error report, а не терять молча.
14. Для больших бинарных форматов хранить raw file reference и parsed summary.
15. Для TEST данных не выполнять обучающие преобразования.
16. Для каждого Parquet artifact хранить row_count.
17. Для каждого этапа формировать report.
18. Любая агрегация должна быть воспроизводимой через ссылку на source artifact.
19. Если данные невозможно разобрать полностью, статус должен быть PARTIALLY_PARSED, а не SUCCESS.
20. Нельзя удалять unknown поля без сохранения в raw_fields_json.


# =======
10. Data quality checks

Для каждого parser-а и normalized artifact нужно проверять:

- количество файлов;
- количество прочитанных строк/событий;
- количество успешно обработанных строк/событий;
- количество ошибок;
- количество пустых строк;
- количество missing values;
- количество duplicate rows;
- schema mismatch count;
- timestamp coverage;
- label coverage;
- label distribution;
- наличие TRAIN/VALIDATION/TEST role;
- наличие branch;
- наличие source_format;
- наличие file_id;
- наличие raw_file_path;
- наличие parser_version;
- наличие schema_version;
- output parquet path.

Минимальные статусы обработки:
- NEW;
- PARSING;
- PARSED;
- PARTIALLY_PARSED;
- FAILED;
- SKIPPED;
- NORMALIZED;
- FEATURE_EXTRACTED;
- MODEL_READY.


# =======
11. Предотвращение data leakage

Критичные правила:

1. TRAIN используется для обучения scaler, encoder, feature selector и модели.
2. VALIDATION используется для настройки threshold, проверки false positives и выбора конфигурации.
3. TEST используется только для финальной оценки.
4. TEST нельзя использовать для fit scaler.
5. TEST нельзя использовать для fit encoder.
6. TEST нельзя использовать для feature selection.
7. TEST нельзя использовать для настройки threshold.
8. TEST нельзя использовать для заполнения missing values на основе общей статистики.
9. Нельзя объединять TRAIN и TEST перед preprocessing fit.
10. Нельзя смешивать DNS и Host данные без явного поля branch/modality.
11. Нельзя менять role датасета после создания model-ready artifacts без пересборки pipeline.
12. Все preprocessing objects должны сохраняться с версией.

Правильный порядок:

1. Load TRAIN features.
2. Fit scaler/encoder on TRAIN only.
3. Transform TRAIN.
4. Transform VALIDATION using TRAIN-fitted objects.
5. Transform TEST using TRAIN-fitted objects.
6. Save preprocessing artifacts.
7. Register artifacts in PostgreSQL.


# =======
12. Что не входит в этап 2

На этапе нормализации не нужно:

- обучать модель;
- подбирать гиперпараметры;
- проводить финальную оценку модели;
- строить SHAP-отчёты;
- выполнять окончательный feature selection;
- объединять все данные в один общий CSV;
- загружать все события в одну таблицу PostgreSQL;
- изменять raw datasets;
- удалять проблемные raw-файлы;
- смешивать TRAIN, VALIDATION и TEST;
- использовать TEST для обучения preprocessing;
- сохранять полный packet payload в PostgreSQL;
- вручную исправлять исходные файлы.

# =======
15. Итоговая суть этапа

Этап 2 нужен для того, чтобы перейти от простого анализа и сортировки датасетов к управляемой подготовке данных для ML/DL pipeline.

Итоговая логика этапа:

- ЭТАП 1 отвечает на вопрос: какие файлы есть, какие форматы найдены, что внутри файлов и пригодны ли они к обработке.
- ЭТАП 2 отвечает на вопрос: как безопасно, воспроизводимо и без потери данных привести эти файлы к единой нормализованной структуре.

Главный результат ЭТАПА 2:
должен появиться нормализованный слой данных, который сохраняет связь с исходными файлами, поддерживает TRAIN/VALIDATION/TEST разделение, хранится в Parquet, управляется через PostgreSQL и анализируется через DuckDB.

Финальный вердикт:

Для дипломного проекта используется архитектура:

PostgreSQL + Parquet/DuckDB

где:

- PostgreSQL хранит метаданные, статусы, связи и контроль pipeline;
- Parquet хранит большие нормализованные события и feature tables;
- DuckDB обеспечивает SQL-доступ и аналитику по Parquet;
- raw-файлы остаются неизменными;
- данные не теряются, потому что все нестандартные поля сохраняются в raw_fields_json/features_json;
- TRAIN, VALIDATION и TEST не смешиваются;
- TEST не используется для обучения preprocessing и модели.

Этап считается выполненным, если после него можно надежно перейти к feature engineering, sequence modelling, обучению моделей, тестированию и explainability analysis без повторного ручного анализа исходных файлов.
