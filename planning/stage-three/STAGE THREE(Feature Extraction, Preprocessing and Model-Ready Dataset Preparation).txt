Stage Three: Feature Extraction, Preprocessing and Model-Ready Dataset Preparation
Документация следующего этапа после Stage Two
Проект: Proposal — Behaviour-driven hybrid learning for data exfiltration detection
Дата подготовки: 2026-07-04

================================================================================
1. НАЗНАЧЕНИЕ ДОКУМЕНТА
================================================================================

Этот документ описывает следующий этап после Stage Two normalization.
Этап рекомендуется называть:

    Stage Three — Feature Extraction, Preprocessing and Model-Ready Dataset Preparation

Главная цель Stage Three:

    преобразовать normalized Parquet artifacts, созданные Stage Two, в корректные,
    воспроизводимые, leakage-safe и split-safe model-ready datasets для последующего
    обучения и оценки моделей RF, XGBoost, CNN и LSTM.

Stage Three не должен заменять Stage Two. Он начинается только после того, как Stage Two
успешно выполнил:

- catalog ingestion;
- parser registry / parser coverage;
- mark-ready workflow;
- normalization в Parquet;
- DuckDB quality checks;
- leakage checks;
- traceability checks;
- регистрацию normalized artifacts в PostgreSQL Catalog.

Общая линия данных проекта:

    raw -> normalized -> features -> model-ready -> training/evaluation

Stage Two закрывает участок:

    raw -> normalized

Stage Three закрывает участок:

    normalized -> features -> model-ready

Следующий этап после Stage Three должен закрывать:

    model-ready -> model training -> evaluation -> SHAP/explainability

================================================================================
2. ГРАНИЦЫ STAGE THREE
================================================================================

2.1. Что входит в Stage Three
-----------------------------

Stage Three включает следующие работы:

1. Проверка готовности Stage Two outputs.
2. Формализация machine-readable feature catalogue.
3. Feature extraction из normalized Parquet artifacts.
4. Построение признаков на уровнях:
   - event-level;
   - window-level;
   - flow-level;
   - trace-level;
   - sequence-level;
   - hybrid-level.
5. Label alignment для event/window/sequence samples.
6. Отделение X, y, metadata и traceability.
7. Приведение признаков к типам, совместимым с ML/DL.
8. Обработка пропусков.
9. Кодирование категориальных признаков.
10. Масштабирование признаков.
11. Балансировка классов только на TRAIN.
12. Сборка model-ready artifacts.
13. Регистрация feature/model-ready/preprocessing artifacts в PostgreSQL Catalog.
14. Data quality checks.
15. Leakage checks.
16. Traceability checks.
17. Генерация итоговых отчетов Stage Three.

2.2. Что не входит в Stage Three
--------------------------------

Stage Three не должен включать:

- обучение Random Forest;
- обучение XGBoost;
- обучение CNN;
- обучение LSTM;
- подбор гиперпараметров моделей;
- late fusion между branches/models;
- SHAP / XAI explanations;
- финальную experimental evaluation;
- comparison с baselines;
- оформление research results.

Эти задачи должны быть вынесены в следующий этап:

    Stage Four — Model Training, Evaluation and Explainability

================================================================================
3. КЛЮЧЕВЫЕ ИНВАРИАНТЫ
================================================================================

Stage Three должен строго соблюдать проектные инварианты.

3.1. Split isolation
--------------------

TRAIN, VALIDATION и TEST нельзя смешивать.

Разрешено:

- TRAIN использовать для обучения и fit preprocessing;
- VALIDATION использовать для настройки и проверки устойчивости;
- TEST использовать только для финальной оценки/inference.

Запрещено:

- использовать TEST для training;
- использовать TEST для fit imputer/scaler/encoder;
- использовать TEST для feature selection;
- использовать TEST для threshold tuning;
- использовать TEST для балансировки классов;
- смешивать rows из разных roles в одном X artifact без явного split_index.

3.2. Raw immutability
---------------------

Raw-файлы не изменяются.

Stage Three не должен напрямую работать с raw dataset files как с основным источником.
Основной вход Stage Three:

    PATH_DATA_STORAGE/parquet/normalized/

Допускается обращаться к raw-файлам только для отладки traceability/parser issues,
но не для production feature extraction.

3.3. Label safety
-----------------

Labels не являются input features.

Поля label_* должны храниться отдельно от X:

- label_binary;
- label_family;
- label_subtype;
- label_source;
- label_status;
- label_confidence;
- label_mapping_rule_id.

Отсутствующий label не означает benign.

Если label отсутствует, нужно сохранять:

    label_binary = null
    label_source = none
    label_status = unlabeled

3.4. Leakage prevention
-----------------------

В model-ready X запрещено включать:

- label_binary;
- label_family;
- label_subtype;
- label_source;
- label_status;
- label_confidence;
- label_mapping_rule_id;
- dataset_name;
- dataset_role;
- source_file;
- source_path;
- file basename;
- scenario_name;
- parser_name;
- parser_version;
- raw_fields_json;
- metadata_json;
- absolute local paths;
- traceability identifiers как признаки модели.

Эти поля допустимы только в metadata/traceability artifacts.

3.5. Timestamp safety
---------------------

Если timestamp отсутствует, запрещено подставлять текущее время.

Корректные варианты:

- timestamp = null;
- timestamp_type = missing;
- использовать event_order, если порядок событий надежно известен;
- для sequence modelling использовать ordering policy, а не synthetic current time.

3.6. Traceability
-----------------

Каждый feature artifact и model-ready artifact должен иметь восстановимую цепочку:

    model_ready_artifact
    -> feature_artifact
    -> normalized_artifact
    -> parser_run
    -> dataset_file
    -> dataset
    -> raw source

4. ПРАВИЛЬНАЯ ПОСЛЕДОВАТЕЛЬНОСТЬ ДЕЙСТВИЙ
================================================================================

Исходный список пользователя:

- feature extraction;
- обработка пропусков;
- масштабирование признаков;
- балансировка классов;
- разметка данных;
- приведение данных в типы числовой, бинарный, bool для обучения модели.

Правильная последовательность должна быть такой:

0. Stage Two readiness gate.
1. Feature catalogue contract.
2. Feature extraction.
3. Feature artifact registration.
4. Label alignment для event/window/sequence.
5. X/y/metadata/traceability separation.
6. Приведение типов признаков.
7. Обработка пропусков.
8. Categorical encoding.
9. Масштабирование признаков.
10. Балансировка классов только на TRAIN.
11. Sequence window build.
12. Model-ready artifact build.
13. Quality checks.
14. Leakage checks.
15. Traceability checks.
16. Stage Three final report.

Почему именно так:

- feature extraction должен идти первым, потому что без признаков нечего
  типизировать, масштабировать и балансировать;
- label alignment должен идти до сборки y, но labels не должны попадать в X;
- X/y/metadata/traceability нужно разделить до preprocessing, чтобы случайно
  не обработать label/source поля как признаки;
- приведение типов должно идти до imputation/scaling/encoding;
- missing value handling должен выполняться до scaling;
- categorical encoding должен выполняться до передачи данных в большинство ML models;
- scaling выполняется после imputation и encoding;
- class balancing выполняется последним среди preprocessing operations и только на TRAIN.

    PATH_DATA_STORAGE/reports/en/stage-three/

6.2. Типы artifacts
-------------------

Stage Three должен создавать следующие artifacts:

1. feature_artifact

   Назначение:
   - хранит извлеченные признаки;
   - сохраняет metadata;
   - сохраняет traceability;
   - еще может содержать label fields, но они должны быть отделены от X при
     model-ready build.

2. model_ready_X

   Назначение:
   - содержит только признаки модели;
   - не содержит labels;
   - не содержит source/path/scenario/leakage fields;
   - не содержит traceability identifiers как признаки.

3. model_ready_y

   Назначение:
   - содержит target values;
   - может быть binary, multiclass или sequence-level target.

4. model_ready_metadata

   Назначение:
   - содержит audit/evaluation metadata;
   - не используется как X.

5. model_ready_traceability

   Назначение:
   - позволяет восстановить lineage до raw source.

6. model_ready_sequence

   Назначение:
   - хранит sequence tensors/windows для LSTM/CNN-LSTM.

7. split_index

   Назначение:
   - фиксирует rows/sample_uid по TRAIN/VALIDATION/TEST;
   - дополнительно может хранить fold assignment для cross-validation.

8. preprocessing_metadata

   Назначение:
   - хранит imputer/scaler/encoder settings;
   - фиксирует fitted_on_role = TRAIN;
   - хранит версии preprocessing pipeline.

10. FEATURE EXTRACTION
================================================================================

10.1. Общий принцип
-------------------

Feature extraction выполняется только из normalized artifacts.

Pipeline:

    normalized_events -> feature rows -> feature_artifacts

Каждая feature row должна содержать:

- sample_uid;
- feature_artifact_id;
- normalized_artifact_id;
- branch;
- dataset_role;
- feature_group;
- window_id или sequence_id;
- event_count;
- label fields;
- traceability metadata;
- feature columns.

10.2. Уровни feature extraction
-------------------------------

1. Event-level

   Один DNS query, syscall, process event, auth event, packet или log event.

   Подходит для:
   - RF;
   - XGBoost;
   - CNN на табличных признаках.

2. Window-level

   Aggregates по времени, host, source_ip, user, process, domain.

   Подходит для:
   - RF;
   - XGBoost;
   - CNN;
   - hybrid features.

3. Flow-level

   Network flow / 5-tuple.

   Подходит для:
   - RF;
   - XGBoost;
   - network branch.

4. Trace-level

   Syscall/API trace.

   Подходит для:
   - CNN;
   - LSTM;
   - sequence branch.

5. Sequence-level

   Ordered event windows.

   Подходит для:
   - LSTM;
   - CNN-LSTM;
   - temporal attack pattern modelling.

6. Hybrid-level

   Host + DNS/network correlation.

   Подходит для:
   - late fusion;
   - hybrid behavioural analysis;
   - exfiltration sequence detection.

11. LABEL ALIGNMENT
================================================================================

11.1. Назначение
----------------

Label alignment связывает labels с feature rows, windows и sequences.
Это не означает, что labels становятся input features.

Pipeline:

    event labels -> window labels -> sequence labels -> y artifact

11.2. Canonical label fields
----------------------------

Обязательные label fields:

- label_binary;
- label_family;
- label_subtype;
- label_source;
- label_status;
- label_confidence;
- label_mapping_rule_id.

11.3. Label alignment по уровням
--------------------------------

Event-level:

    label берется из конкретного normalized event.

Window-level:

    label назначается по событиям внутри окна.

Sequence-level:

    label назначается по событиям внутри sequence window.

Flow-level:

    label назначается по flow/event mapping.

Hybrid-level:

    label назначается по самому сильному подтвержденному signal внутри окна.

11.4. Рекомендуемые label policies
----------------------------------

1. explicit_only

   Использовать только explicit labels.
   Рекомендуется для строгой supervised evaluation.

2. any_attack_in_window

   Если в окне есть хотя бы одно attack событие, окно получает attack label.
   Рекомендуется для detection-oriented MVP с высоким recall.

3. majority_label

   Label окна определяется большинством событий.
   Рекомендуется для устойчивости к единичным noisy labels.

4. last_event_label

   Label окна определяется последним событием.
   Подходит для sequence forecasting.

5. weak_allowed_with_confidence

   Weak labels разрешаются, но обязательно сохраняется confidence.
   Подходит, если explicit labels мало.

11.5. Запреты label alignment
-----------------------------

Запрещено:

- считать unlabeled как benign;
- использовать filename hint для TEST training logic;
- смешивать labels из VALIDATION/TEST в TRAIN;
- включать label_* поля в X;
- использовать scenario/source/path как признаки модели.

Действие: исключить из X.

14. ОБРАБОТКА ПРОПУСКОВ
================================================================================

14.1. Главный принцип
---------------------

Imputer fit выполняется только на TRAIN.

    TRAIN:      fit imputer + transform
    VALIDATION: transform only
    TEST:       transform only

Запрещено fit imputer на VALIDATION или TEST.

14.2. Типы пропусков
--------------------

1. Реально отсутствующее значение

   Поле отсутствует в источнике.
   Нужно заполнить согласно policy и добавить missing indicator.

2. Not applicable

   Например, DNS field для host event.
   Нужно заполнить 0 или отдельным not_applicable indicator.

3. Parser extraction failure

   Parser не смог извлечь значение.
   Нужно сохранить parser warning и не скрывать проблему.

4. Unknown label

   Label отсутствует.
   Нельзя превращать в benign.

14.3. Missing strategies
------------------------

Numeric counters:

    0, если отсутствие действительно означает ноль;
    иначе median.

Numeric continuous:

    median.

Ratios:

    median или 0 + missing indicator.

Boolean:

    false + missing indicator.

Categorical:

    UNKNOWN category.

Timestamp-derived:

    -1 / UNKNOWN_TIME + timestamp_missing flag.

Sequence:

    padding + mask.

14.4. Preprocessing metadata для imputer
---------------------------------------

Пример:

    {
      "imputer_version": "1.0",
      "fitted_on_role": "TRAIN",
      "numeric_strategy": "median",
      "categorical_strategy": "constant_UNKNOWN",
      "missing_indicators": true,
      "fit_artifact_id": "...",
      "created_at": "..."
    }

15. CATEGORICAL ENCODING
================================================================================

15.1. Назначение
----------------

Категориальные признаки должны быть преобразованы в числовой формат.

15.2. Методы encoding
---------------------

One-hot encoding:

- protocol;
- qtype;
- rcode;
- log_level;
- small-cardinality categories.

Ordinal encoding:

- только если у категории есть реальный порядок.

Frequency encoding:

- process_name;
- event_template;
- domain token class;
- command category.

Hashing trick:

- high-cardinality process names;
- command tokens;
- file path tokens, если они очищены от leakage.

Embedding index:

- sequence models;
- syscall tokens;
- API calls;
- event type tokens.

15.3. Запрещенные категории для encoding
----------------------------------------

- dataset_name;
- dataset_role;
- source_file;
- source_path;
- scenario_name;
- label_source;
- label_status;
- parser_name;
- parser_version.

16. МАСШТАБИРОВАНИЕ ПРИЗНАКОВ
================================================================================

16.1. Главный принцип
---------------------

Scaler fit выполняется только на TRAIN.

    TRAIN:      fit scaler + transform
    VALIDATION: transform only
    TEST:       transform only

16.2. Когда scaling нужен
-------------------------

Random Forest:

    scaling обычно не обязателен.

XGBoost:

    scaling обычно не обязателен.

CNN:

    scaling желателен.

LSTM:

    scaling желателен или обязателен, особенно для continuous features.

Logistic Regression / SVM:

    scaling обязателен.

SMOTE:

    scaling желателен до применения, так как SMOTE distance-based.

16.3. Scaling profiles
----------------------

1. tree_unscaled

   Для RF/XGBoost.
   Содержит imputed + encoded features без scaling.

2. standard_scaled

   StandardScaler для DL/linear models.

3. robust_scaled

   RobustScaler для признаков с выбросами.

4. minmax_scaled

   MinMaxScaler для neural networks, если нужен диапазон [0, 1].

16.4. Рекомендация для проекта
------------------------------

Создавать минимум два model-ready варианта:

17. БАЛАНСИРОВКА КЛАССОВ
================================================================================

17.1. Главный принцип
---------------------

Балансировка выполняется только на TRAIN.

Запрещено:

- SMOTE на VALIDATION;
- SMOTE на TEST;
- undersampling VALIDATION;
- undersampling TEST;
- oversampling VALIDATION;
- oversampling TEST;
- threshold tuning на TEST.

17.2. Методы балансировки
-------------------------

1. class_weight

   Первый безопасный baseline.
   Рекомендуется для MVP.

2. scale_pos_weight

   Для XGBoost при дисбалансе классов.

3. Random undersampling

   Можно использовать, если benign rows слишком много и обучение слишком медленное.

4. Random oversampling

   Можно использовать, если attack minority слишком мал.

5. SMOTE

   Только после numeric preprocessing.
   Должен быть disabled by default.
   Требует отдельной ablation-проверки.

6. Focal loss

   Для DL-моделей на следующем этапе.

17.3. Рекомендация для MVP
--------------------------

Для первого стабильного pipeline:

1. Не применять SMOTE сразу.
2. Использовать class_weight / scale_pos_weight.
3. Сформировать class balance report.
4. Позже отдельно сравнить undersampling/oversampling/SMOTE как ablation.

Причина:

    SMOTE может создавать искусственные attack samples, которые плохо отражают
    реальные cybersecurity events.

17.4. Class balance report
--------------------------

21. LEAKAGE PREVENTION
================================================================================

21.1. Critical leakage fields
-----------------------------

Запрещены в X:

- label_binary;
- label_family;
- label_subtype;
- label_source;
- label_status;
- label_confidence;
- label_mapping_rule_id;
- dataset_name;
- dataset_role;
- source_file;
- source_path;
- scenario_name;
- parser_name;
- parser_version;
- raw_fields_json;
- metadata_json;
- local absolute paths;
- raw payload/body;
- traceability IDs как model features.

21.2. Critical leakage scenarios
--------------------------------

CRITICAL:

- TEST rows внутри TRAIN artifact;
- labels внутри X;
- source/path/scenario fields внутри X;
- preprocessing fit на VALIDATION/TEST;
- feature selection с использованием TEST;
- threshold tuning с использованием TEST;
- filename label hints в TEST training logic.

ERROR или CRITICAL по контексту:

- weak labels используются как ground truth без label_status/confidence;
- missing labels превращаются в benign;
- scenario metadata используется как input feature.

21.3. Blocking policy
---------------------

Если leakage check возвращает CRITICAL, artifact нельзя использовать downstream.

Artifact должен получить статус:

    BLOCKED_BY_LEAKAGE
