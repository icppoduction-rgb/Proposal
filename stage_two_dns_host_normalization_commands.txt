1. Профили запуска
------------------

Текущий ноутбук, 16 GB RAM + файл подкачки:

--workers 1 --batch-size 10000 --max-output-part-rows 50000 --resume

Использовать, когда:
- один или два файла очень большие, примерно 8-17 GB;
- RAM доходит до 90%+;
- диск занят из-за pagefile/swap Windows.

Текущий ноутбук после разбиения больших line-based файлов:

--workers 2 --batch-size 10000 --max-output-part-rows 50000 --resume

Использовать только после того, как split-large-files зарегистрировал chunks.
Следить за Диспетчером задач.
Если RAM держится ниже 12-14 GB и диск не висит на 100%, можно оставлять этот режим.
Если RAM или диск забиты, остановить и перезапустить с --workers 1.

Профиль для 64 GB RAM:

--workers 2 --batch-size 25000 --max-output-part-rows 50000 --resume

Профиль для 128 GB RAM:

--workers 4 --batch-size 50000 --max-output-part-rows 100000 --resume

Для packet capture форматов можно использовать:

--packet-mode dns-only

для DNS pcap/cap/pcapng, если не нужны summary по не-DNS пакетам.


2. Важное поведение параметров
------------------------------

--limit ограничивает количество файлов, а не количество строк.
Например, --limit 100 означает до 100 файлов из catalog.

--workers параллелит файлы, а не строки внутри одного файла.
Для одного большого файла workers > 1 почти не поможет, пока файл не разбит на chunks.

--batch-size управляет давлением parser-а на память.
Меньше значение = безопаснее для RAM, но больше накладных расходов.
Больше значение = иногда быстрее, но требует больше RAM.

--max-output-part-rows управляет размером Parquet part.
Для больших запусков 50000 или 100000 обычно лучше, чем 10000, потому что не создается слишком много мелких Parquet файлов.

--resume помогает только если уже есть resumable parser_run и зарегистрированные output parts.
Если был KeyboardInterrupt до commit parser_run, продолжать может быть нечего.

Не запускай одновременно исходный большой файл и его chunks.
Команда split-large-files с --register по умолчанию помечает исходный файл как SKIPPED, поэтому normalize-format обрабатывает только chunks.


3. Разбиение больших line-based файлов
--------------------------------------

Использовать split для больших line-based форматов:

csv, pcap.csv, txt, json/json-lines, log, auth.log, syslog*, mainlog*, messages*,
ghc, sc, netflow_day, netflow_ids, wls_day, cpu.log, diskio.log, filesystem.log,
fsstat.log, load.log, memory.log, network.log, process.log, process.summary.log,
service.log, socket.summary.log, uptime.log.

Не использовать split для бинарных packet форматов:

cap, pcap, pcapng, bson

DNS TEST csv без header, поэтому использовать --header no.

Проверка без записи:

python manage.py stage-two split-large-files --branch dns --role TEST --format csv --limit 1 --max-part-size-gb 2 --min-size-gb 1 --header no

Записать chunks и зарегистрировать их в catalog:

python manage.py stage-two split-large-files --branch dns --role TEST --format csv --limit 1 --max-part-size-gb 2 --min-size-gb 1 --header no --apply --register

После этого нормализовать chunks параллельно:

python manage.py stage-two normalize-format --branch dns --role TEST --format csv --limit 4 --workers 2 --batch-size 10000 --max-output-part-rows 50000 --resume

Для CSV с header использовать --header yes или --header auto.


4. Повторный запуск failed / partial файлов
-------------------------------------------

Если normalize-format вернул PARTIAL_SUCCESS/FAILED и нужно повторить только failed/skipped/partially parsed файлы:

python manage.py stage-two mark-ready --branch <branch> --role <role> --format <format> --retry-failed --dry-run
python manage.py stage-two mark-ready --branch <branch> --role <role> --format <format> --retry-failed --apply
python manage.py stage-two normalize-format --branch <branch> --role <role> --format <format> --limit 100 --workers 1 --batch-size 10000 --max-output-part-rows 50000 --resume

Не сбрасывай PARSED файлы, если не хочешь намеренно обработать успешные данные заново.
