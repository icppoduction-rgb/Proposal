Команды Stage Two для DNS/HOST по parser_active.txt
=========================================================================

Актуализировано: 2026-06-20.

Важно после исправления DNS CSV / Parquet mixed JSON fields:
- Если normalize-format уже вернул PARTIAL_SUCCESS и часть файлов получила статус FAILED,
  обычный mark-ready --apply их не поднимет повторно.
- Для повторной обработки таких файлов использовать mark-ready --retry-failed.
- --retry-failed переводит только FAILED, SKIPPED и PARTIALLY_PARSED в READY_FOR_PARSING.
- PARSED не трогать: уже успешно нормализованные файлы не должны перезаписываться без отдельной причины.

Исходный файл:
C:\Users\fmark\OneDrive\Desktop\Заметки\parser_active.txt

Что включено в список:
- Включены только строки, где action = ready_for_normalization и files_count > 0.
- Строки parser_available_empty_bucket не включены в рабочие команды, потому что сейчас в catalog нет файлов для этой связки branch/role/format.
- Рабочие роли Stage Two: TRAIN, VALIDATION, TEST.
- EXPERIMENTS в Stage Two не используется.
- Все команды нужно выполнять из корня репозитория:
  C:\Users\Public\PythonProjects\Proposal

Общая последовательность
------------------------

0. Подготовительные команды выполняются один раз перед нормализацией, если они еще не выполнялись:

python manage.py stage-two bootstrap-storage
python manage.py stage-two alembic upgrade head
python manage.py stage-two alembic current
python manage.py stage-two seed-parser-registry
python manage.py stage-two catalog-ingest

1. Проверить покрытие parser registry и catalog:

python manage.py stage-two parser-coverage

1.1. Перед массовой нормализацией желательно проверить кодовую базу:

python -m compileall -q manage.py config.py scripts tests
python -m pytest -q
python -m scripts.stage_two.parser_smoke
python -m scripts.stage_two.parser_input_smoke
python -m scripts.stage_two.parser_catalog_smoke
python -m scripts.db.smoke_check

2. Дальше для каждой новой связки branch/role/format выполнять обычный поток:

   2.1. mark-ready --dry-run
        Проверяет, сколько файлов будет выбрано. Ничего не меняет в БД.

   2.2. mark-ready --apply
        Переводит выбранные файлы из REGISTERED, CHANGED, DISCOVERED в READY_FOR_PARSING.
        Выполнять только если dry-run показал ожидаемые selected/eligible и нет ошибок.

   2.3. normalize-format
        Нормализует выбранный формат в Parquet artifacts.
        --limit 100 означает максимум 100 файлов catalog dataset_files за один запуск, не 100 строк внутри CSV/логов.

2.4. Если предыдущий normalize-format завершился PARTIAL_SUCCESS/FAILED и нужно повторить только проблемные файлы:

python manage.py stage-two mark-ready --branch <branch> --role <role> --format <format> --retry-failed --dry-run
python manage.py stage-two mark-ready --branch <branch> --role <role> --format <format> --retry-failed --apply
python manage.py stage-two normalize-format --branch <branch> --role <role> --format <format> --limit 100 --workers 2 --batch-size 50000 --max-output-part-rows 50000 --resume

   В retry-режиме mark-ready выбирает только FAILED, SKIPPED и PARTIALLY_PARSED.
   Это штатный сценарий восстановления после частичной нормализации.

2.5. Отчеты mark-ready сохраняются относительно PATH_DATA_STORAGE:

reports/en/stage-two/status/mark_ready_<branch>_<role>_<format>_<initial|retry_failed>.md
reports/en/stage-two/status/mark_ready_<branch>_<role>_<format>_<initial|retry_failed>.json
reports/ru/stage-two/status/mark_ready_<branch>_<role>_<format>_<initial|retry_failed>.md
reports/ru/stage-two/status/mark_ready_<branch>_<role>_<format>_<initial|retry_failed>.json

3. Рекомендуемый порядок:

   3.1. Сначала DNS: он меньше и проще для проверки.
   3.2. Затем HOST небольшие форматы.
   3.3. HOST ghc, txt, bson, json, log запускать ближе к концу, потому что там много файлов.
   3.4. Не смешивать роли: TRAIN, VALIDATION, TEST выполняются отдельными командами.

4. Массовую нормализацию запускать только после точечной проверки отдельных форматов:

python manage.py stage-two normalize-all --branch dns --limit 1000 --workers 2 --batch-size 50000 --max-output-part-rows 50000 --resume
python manage.py stage-two normalize-all --branch host --limit 1000 --workers 2 --batch-size 50000 --max-output-part-rows 50000 --resume

5. После нормализации выполнить проверки:

python manage.py stage-two run-duckdb-checks
python manage.py stage-two run-leakage-checks
python -m scripts.stage_two.readiness_check

Large-file performance flags (recommended for PCAP/PCAPNG/CAP and large text formats):

python manage.py stage-two normalize-format --branch dns --role TRAIN --format pcap --limit 100 --workers 2 --batch-size 50000 --max-output-part-rows 50000 --packet-mode dns-only --resume
python manage.py stage-two normalize-all --branch host --limit 1000 --workers 2 --batch-size 50000 --max-output-part-rows 50000 --resume

Notes:
- --workers uses ProcessPoolExecutor at file level; CPU-bound parsing does not use threads.
- --batch-size controls parser batches; --max-output-part-rows controls Parquet part size.
- --packet-mode accepts packet-summary, dns-only, sample; use --sample-size with sample.
- --resume reuses a resumable parser_run and skips registered part_index values.
- Output Parquet hashing is disabled by default; use --hash-output-artifacts only when needed.
