Назначение файла
================

Этот файл — единая техническая документация по коду репозитория в формате .txt.
Это не простая склейка исходников, а структурированное описание архитектуры,
точек входа, модулей, потоков данных, контрактов, CLI-команд, тестов,
ограничений и зон развития.

На момент анализа в репозитории:

- 236 Python-файлов кода и тестов;
- 37 Python-файлов тестов, почти все относятся к Stage Two;
- JSON-схемы для normalized, feature и model-ready артефактов;
- русская и английская документация в docs/;
- planning-материалы по Stage One и Stage Two.

Главная логика проекта делится на два этапа:

1. Stage One — поиск, фильтрация, сортировка, инвентаризация и анализ
   DNS/Host датасетов.
2. Stage Two — catalog-backed нормализация данных: PostgreSQL Catalog,
   parser registry, нормализация в Parquet, DuckDB/data quality checks,
   leakage checks, traceability и базовые contracts для feature/model-ready
   слоев.


1. Текущее состояние реализации
===============================

Готово и подтверждено кодом:

- CLI через manage.py и scripts/router_script.py.

  генерации отчетов по DNS/Host форматам.

  schemas, preprocessing и quality reports.
- Alembic migration для Stage Two catalog schema.
- Storage bootstrap для PATH_DATA_STORAGE.
- Catalog ingestion из PATH_FOLDER_DATASETS_FILTER.
- Parser registry seed и resolver.
- Parser coverage и mark-ready workflow.
- Нормализация точного bucket через normalize-format.
- Batch-нормализация ветки через normalize-all.
- Legacy normalize-dns / normalize-host.
- Benchmark normalization.
- Splitter больших line-based файлов.
- Набор Stage Two parser implementations.
- Parquet writer.
- DuckDB analytics layer.
- DataQualityChecker / LeakageChecker.
- Post-run validation.
- Traceability service.
- Readiness check и e2e dry-run.
- Feature/model-ready contracts и writer/registry services.

Не готово как полный end-to-end ML pipeline:

- полноценный CLI для feature extraction;

- preprocessing fit/transform orchestration;
- обучение RF/XGBoost/CNN/LSTM;
- SHAP/explainability pipeline;
- финальные experiment/evaluation reports.

Практический вывод:

Код сейчас наиболее готов для воспроизводимой подготовки данных,
нормализации, каталогизации, проверки качества и контроля leakage. ML-слой
после model-ready contracts пока остается follow-up/proposal work.


2. Точки входа и маршрутизация
==============================

2.1 manage.py
-------------

Назначение:

- главная CLI-точка входа;
- принимает positional arguments:
  - module;
  - service;
  - action;
  - extra_args;
- передает управление в scripts.router_script.router_commands().

Форма запуска:

python manage.py <module> <service> <action> [extra args]

Примеры:

python manage.py handlers analyze-dataset dns-dataset-handler
python manage.py handlers sort sort-host-dataset-handler
python manage.py stage-two bootstrap-storage
python manage.py stage-two normalize-format --branch host --role TEST --format txt --resume

2.2 scripts/router_script.py
----------------------------

Назначение:

- верхнеуровневый router;
- module == handlers отправляет в scripts.handlers.router_handler;
- module == stage-two отправляет в scripts.stage_two.cli.router_stage_two;
- неизвестный module печатает fallback help из config.manage_commands.

Важное ограничение:

config.manage_commands — не полный источник правды по Stage Two. Для Stage Two
актуальный источник команд — scripts/stage_two/cli.py.

2.3 config.py
-------------

Назначение:

- загружает .env через python-dotenv;
- определяет PROJECT_ROOT;
- определяет пути к датасетам, storage, reports, temp_data, schemas и docs;
- хранит Stage Two runtime defaults;
- хранит DATABASE_URL;
- хранит fallback help manage_commands.

Ключевые переменные окружения:

- PATH_DATA_STORAGE;
- PATH_FOLDER_DATASETS;
- PATH_FOLDER_DATASETS_FILTER;
- DATABASE_URL;
- STAGE_TWO_PARQUET_COMPRESSION.

Ключевые Stage Two defaults:

- STAGE_TWO_DEFAULT_WORKERS = 1;
- STAGE_TWO_DEFAULT_BATCH_SIZE = 50000;
- STAGE_TWO_MAX_OUTPUT_PART_ROWS = 50000;
- STAGE_TWO_PACKET_BATCH_SIZE = 50000;
- STAGE_TWO_PACKET_PARSE_MODE = packet-summary;
- STAGE_TWO_TEXT_ENCODINGS включает utf-8, utf-16, cp1251, latin-1.

Безопасность:

- .env в документацию не переносится;
- реальные секреты, URL БД и пароли не должны попадать в docs или git.

6.3 scripts/db/models/
---------------------

Основные модели:

- Dataset — metadata датасета на уровне source group и split role.
- DatasetFile — один raw-файл в catalog: путь, hash, размер, role, branch,
  source_format, status, hints и metadata.
- IngestionRun — история запуска catalog ingestion.
- ParserRegistry — registry parser metadata по branch/source_format/role.
- ParserRun — один запуск parser/normalization по конкретному file_id.
- SchemaVersion — зарегистрированные схемы.
- LabelMappingRule — правила label mapping.
- NormalizedArtifact — Parquet artifact после parser run.
- FeatureArtifact — Parquet artifact после feature extraction.
- ModelReadyArtifact — X/y/sequence/split/preprocessing metadata artifact.
- PreprocessingArtifact — scaler/encoder/imputer artifact, fit только на TRAIN.
- DataQualityReport — результаты quality/leakage/check reports.

Важные constraints:

- branch, role, status, severity и data_type ограничены allowed values;
- Dataset уникален по name/branch/role и slug/branch/role;
- DatasetFile уникален по dataset_id/file_path;
- PreprocessingArtifact имеет CHECK fitted_on_role = TRAIN.

19. Инварианты безопасности и корректности
==========================================

Raw safety:

- raw-файлы не изменяются;
- Stage Two создает metadata и artifacts;
- большие таблицы хранятся в Parquet;
- PostgreSQL хранит metadata/status/path/hash/report/lineage.

Split safety:

- TRAIN, VALIDATION и TEST не смешиваются;
- TEST не используется для training;
- TEST не используется для fit preprocessing/scaler/encoder;
- TEST не используется для feature selection;
- TEST не используется для threshold tuning/model selection.

Label safety:

- labels не являются input features;
- missing label не означает benign;
- filename/scenario/path hints требуют audit trail;
- TEST label hints ограничены.

Leakage safety:

- label/source/path/scenario/traceability fields не должны попадать в X;
- contracts и LeakageChecker контролируют forbidden columns.

Timestamp safety:

- missing timestamp остается missing;
- current time нельзя подставлять как event timestamp;
- event_order используется только как порядок событий, а не абсолютное время.

Traceability:

- raw -> normalized -> features -> model-ready должна оставаться восстанавливаемой.

22. Основные риски и technical debt
===================================

Code/runtime risks:

- Host datasets сильно неоднородны;
- большие txt/log/syscall/netflow files требуют streaming;
- PCAP/PCAPNG/CAP/BSON требуют специализированной обработки;
- mixed JSON/log schemas могут drift-ить;
- Stage One analyzer files крупные и повторяющиеся.

Docs/runtime risks:

- config.manage_commands устарел относительно Stage Two CLI;
- актуальный Stage Two help нужно брать из scripts/stage_two/cli.py;
- часть docs описывает proposal-level планы, а не готовый ML pipeline.

ML gaps:

- нет полного feature extraction CLI;
- нет полного model-ready build CLI;
- нет preprocessing fit/transform orchestration;
- нет training code для RF/XGBoost/CNN/LSTM;
- нет SHAP/evaluation reports.

Leakage risks:

- TEST contamination;
- filename/source/scenario leakage;
- labels случайно попадают в X;
- weak labels трактуются как ground truth без confidence/audit.

25. Итог
========

Проект Proposal — Python data engineering кодовая база для подготовки DNS/Host
датасетов, нормализации heterogeneous raw-файлов и подготовки контролируемой
основы для ML.

Stage One готовит файловую структуру и документацию по данным. Stage Two
реализует backend-подобный pipeline: PostgreSQL Catalog, parser registry,
streaming-aware parsers, normalized Parquet artifacts, performance controls,
quality checks, leakage checks и traceability.

Код уже пригоден для контролируемых normalization runs по точным
branch/role/source_format buckets. Полный ML слой — feature extraction,
model-ready build, preprocessing, training, evaluation и explainability —
требует дальнейшей реализации.
